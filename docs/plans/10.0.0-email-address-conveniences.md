# Email address conveniences and copying documentation

Date: 2026-10-20. Decisions: 2a, 2b and documentation-only 6a from the
[public API review](../research/10.0.0-public-api-options.md). Status: implementation and verification complete.

## Baseline and scope

HEAD remains `69c483280394a743b5b73312ed0fcfc3dfd972d5`; the already completed grouped-configuration implementation is an
uncommitted working-tree baseline. Its independent [Javadoc audit](../research/10.0.0-grouped-api-javadoc-audit.md)
passed before this job and was not rewritten. Existing root/nested-website changes and index entries are preserved.

The Email-only helper `EmailAddressConvenience` applies the accepted single-mailbox interpretation to existing
String and equivalent InternetAddress conveniences for From, To/Cc/Bcc, Reply-To, bounce and receipt-request addresses.
An explicit nonblank name wins; null/blank uses the embedded name. Quoted punctuation and encoded display names remain
one mailbox. Successfully parsed lists and RFC groups are argument errors; nonempty unparseable or mailbox-free input
is retained for the configured send-time validator. Required arguments and nullable bounce clearing retain their
separate boundaries. No DNS/deliverability check or new public parsing family was introduced.

`IRecipientBuilder`, `IRecipientsBuilder`, their implementations, specialized address helpers and shared first-mailbox
interpretation are unchanged. Prepared Recipient values remain authoritative. The CLI's existing plural address
options retain their independent parser. New Java conveniences were not retroactively treated as released 9.x APIs.

Reply-To stays additive. Javadocs now state repeated-call, order, duplicate, empty-input and copied-collection behavior
for additive address methods. `withReplyTo(emptyList())` and `withRecipients(emptyCollection/array)` add nothing;
`withOverrideReceivers(empty)` retains its existing required-input exception. Clearing before adding replacements is
documented without changing From/Bounce/receipt scalar replacement or template/lock behavior.

Copying retains the original borrowed-content, suppression, recipient-metadata and merged-S/MIME caveats. The exact-copy
clarification states that ordinary copying starts editable composition and guarantees neither original byte identity
nor validity of already applied signatures; it does not automatically remove or re-sign them. Existing-API examples
reuse the original exact Email, or construct another exact envelope from authoritative finalized input. No new exact
copy mode, message type or signature behavior was added.

## License-formatter interruption and recovery

The first JDK 17 package failed in Mycila's license formatter because Windows reported a user-mapped source section.
Its parallel formatting truncated 16 main-module Java files to zero bytes before reporting the failure. Maven was
stopped; a subsequent compiler cascade was not treated as a parsing-code defect.

Only zero-byte files were restored from the successful JDK 11 verification's **current-working-tree sources JAR**,
not HEAD. Its retained SHA-256 is `3649bd39e1495dbfcdf77ef204a609d49268d262991f0ce1581443b83ed9930c`.
The archive includes the completed grouping work and this job's helper. None of the 16 files had post-archive source
edits: the helper was written before that verification, and other source owners had stopped before this job.
Every main-module Java source matches that successful archive after normalizing generated headers/newlines;
no nonempty source was overwritten and no zero-byte Java source remains. `formatter-recovery.json` records each
restored path/hash; `java11-current-working-tree-sources.jar` retains the recovery input.
The broader scan found no empty files among 1,356 nonignored root-repository and 344 nested-website files, including
non-source files and other modules (`empty-worktree-scan.json`). This is an actual post-recovery scan, not an inference
about which Windows process held the mapping; that process was not identified.

Fresh compilation and package regeneration then passed with only license mutation skipped. Subsequent verification
also uses `-Dlicense.skip=true`. Keep this flag for the next local source job until the formatter/Windows interaction
is handled separately. Remaining generated header boilerplate is removed safely without rerunning the failed formatter.
Fifteen header-only edits were checked against the successful archive, backed up and removed by atomic replacement;
the unchanged source body was rechecked before replacement. No source was truncated during cleanup. The full checkpoint
is also retained outside Maven targets before handing the build slot back; its location is in `retained-evidence-location.txt`.

CLI adapter Javadoc while the public group contract contained `José`/`josé`. A controlled UTF-8-only generation did
not change that source defect. Repairing those four strings restores the existing facts without changing CLI behavior
or weakening the test. It is separate from the Windows mapping failure and does not imply a diagnosed JVM charset bug.
