## Inventory and design

- Root: `MailException`; existing `MailSendException` retains its role as a more specific send-failure base.
- Admission: built-in queue rejection and borrowed-executor rejection, including sends attempted after Mailer shutdown.
- Validation/size/preparation: preserve useful validation and size exception catches; do not rewrap them in `SendMailClosure` or shared scopes.
- Connection/submission: keep physical setup evidence separate from local credentials/configuration and SMTP refusal/uncertain acceptance.
- Cleanup: retain individual-send receipts after acceptance; keep primary failures and suppress secondary cleanup. Shared scopes have no
  invented aggregate receipt.
- Timeout/cancellation: preserve stop arbitration and any captured receipt through the common root.
- Extension controls: handler/ID factories, iterators, CustomMailer and open-connection callbacks keep their documented identity/propagation;
  observer isolation remains. Invalid API arguments, invariant violations and fatal Errors are outside the common operational catch promise.
- Receipt predicates: rename the former any-recipient convenience and add full-submission acceptance. UNKNOWN false is not proven rejection.

## Verification and propagation ledger

### Final API and producing boundaries

`MailException` exposes final `getKind()` and `Optional<MailSubmissionReceipt> getSubmissionReceipt()` alongside the original cause.
`MailFailureKind` has CONFIGURATION, VALIDATION, MESSAGE_SIZE, PREPARATION, CAPACITY, CONNECTION, SUBMISSION, TIMEOUT,
CANCELLED, CLEANUP, CONVERSION and OTHER. Kind does not establish retry safety. Legacy protected constructors remain usable by external
subclasses and yield OTHER; no historical exception-snapshot compatibility is claimed by this change.

`MailSendException` remains a useful specific base. Size and queue rejection now extend it, so both share `MailException`. A borrowed executor's
`RejectedExecutionException` becomes `MailSendRejectedException(EXECUTOR_REJECTED, originalCause)`; shutdown rejection uses the existing shutdown
reason for both owned and borrowed executors. Built-in queue counters still count their own admissions only.

Send and shared-scope boundaries preserve already classified failures rather than wrapping away useful subclasses. Main/optional producers now
classify their owned configuration, conversion, signing, pool/allowance, connection and cleanup failures. Invalid arguments/invariants remain
argument/state errors. CustomMailer and caller-iteration RuntimeExceptions propagate with their original identity, and stop translation does not
relabel application failures. Existing handler/ID-factory and open-connection callback propagation and observer isolation remain intact.

The attachment regression also caught MIME logging using the standalone EML-export failure family. Sending now normalizes checked MIME/content
failures at its preparation producer and uses its existing internal serializer for logging, preserving the underlying cause. It does not turn
content access into an SMTP submission failure merely because a transport is already connected, or classify the same logging failure as standalone
conversion. No signing, message-content or exact-byte policy changed.

The receipt now exposes `isAcceptedForAtLeastOneRecipient()` and `isFullyAcceptedForSubmission()`; the ambiguous old method is removed.
Truth table: ACCEPTED true/true, PARTIALLY_ACCEPTED true/false, REJECTED false/false, UNKNOWN false/false. Existing legitimate any-recipient
consumers were migrated to ANY, including the method reference. Partial submission still fails, unknown false is not proof of rejection, and accepted
receipts survive later individual-send cleanup failures. Shared-scope cleanup does not invent an aggregate receipt.

### Windows cache-write interruption

The first JDK 17 `publish-cli` generation failed while opening `src/main/resources/cli.data` for writing with Windows's user-mapped-section error.
Both source cache files and both target/classes copies still matched their initial hashes, and no Java source was empty. Those four copies were
backed up outside targets. This was a generated-resource write failure, not another license-formatter source truncation.

The failed Maven process exited. An unrelated Maven-looking Java process created on 13 October was left untouched. The existing CLI generator
then ran outside the checkout with an isolated first resource directory and current reactor classes; the generated bytes match the source caches
exactly, so no source-cache replacement was needed. Distribution packaging uses `publish-cli` with `-Dexec.skip=true` after that verified generation,
plus `-DskipTests` only for this artifact step; the separate normal tests-enabled verification is the test evidence. All Maven commands retain
`-Dlicense.skip=true`. Neither an unknown mapped-file holder nor a general Windows/JVM defect is diagnosed here.
