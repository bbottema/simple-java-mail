# Received Email output/helper inventory, 10 November 2026

Phase 0 inventory frozen by the lead before production edits. The approved plan/ledger govern behavior; this records concrete paths and the implementation surface. Execution/publication evidence stays outside issues and commit messages.

## Actual paths and ownership

- `EmailStartingBuilderImpl.replyingTo(Email, boolean, String)` currently projects headers with `MimeMessageHelper.createReplyHeaders`, calls provider `MimeMessage.reply`, then `primeReply` supplies quoted bodies, embedded resources and generated headers. Exact Email first converts its authoritative MIME. The MimeMessage overload currently calls `reply()` before converting, which must change so logical authored selection is shared.
- `forwarding(Email)` currently makes a finalized artifact immediately through `FromEmail.toMimeMessageResult`, then stores its MimeMessage in `withForward`; `forwarding(MimeMessage)` is the independent borrowed MIME route. `copying(Email)` explicitly restores legacy decrypted/retained-inner/detail state; those lines are removed and the new selection/draft state restored at the end, after setters.
- Ordinary output: `FluentEmailConversions.FromEmail.convert` -> `ExportOptions.exportEmail` -> `ArtifactConversions.Operation.render` -> `InternalEmail.prepareForConversion(governance)` -> optional `stageContent` -> base render/security. `stageContent` copies, clears and re-adds resources, so it must restore helper state after its internal transformations. Public static `EmailConverter.emailToMimeMessage`/EML routes delegate this configured path. `InternalEmailConverterImpl` is an internal module adapter to that same path.
- Sending: `SessionBasedEmailToMimeMessageConverter.convertAndLogMimeMessage` -> `InternalEmail.renderMimeMessage(processSecurity=true)`. `SendMailClosure`, `SendMailsInSimpleBatchClosure`, `SendMailsWithOpenConnectionClosure`, `TransportRunner`, `RoutedMailConnection` and `MailSendRetryingSubmission` converge here before provider/CustomMailer submission. Selected destination governance/locks resolve before this conversion. No guard belongs in an SMTP provider or a source-data predicate.
- Rehearsal: `EmailPreparation` -> `SessionBasedEmailToMimeMessageConverter.rehearseMimeMessage`; even the base-only rehearsal exposes EML bytes, so final release must evaluate helper state against the actually produced artifact. Internal base rendering remains available for later enclosing protection.
- MIME construction: `ComposedEmailSource.renderMimeMessage` -> `MimeMessageProducerHelper` -> one of eight `SpecializedMimeMessageProducer` variants. Security order remains S/MIME sign/encrypt, OpenPGP sign/encrypt, DKIM. `FinalizedMimeMessage.ProtectionState.CONTENT_PROTECTED` includes signatures and cannot establish encryption.
- Governance: `EmailGovernanceImpl.produceEmailApplyingDefaultsAndOverrides` rebuilds from resolved fields. Preserve the submitted draft's helper state after field/template/lock work; templates never supply consent. Exact sources retain their dedicated source/envelope path and authoritative bytes.

## Target supported helper/permission signatures

Keep existing source/default/custom-quotation convenience overloads. Add these typed routes, rather than multiplying quote/permission combinations:

```java
EmailPopulatingBuilder replyingTo(Email email, ReplyOptions options);
EmailPopulatingBuilder replyingToAll(Email email, ReplyOptions options);
EmailPopulatingBuilder replyingTo(MimeMessage message, ReplyOptions options);
EmailPopulatingBuilder replyingToAll(MimeMessage message, ReplyOptions options);
EmailPopulatingBuilder forwarding(Email email, ForwardOptions options);
EmailPopulatingBuilder forwarding(MimeMessage message, ForwardOptions options);
EmailPopulatingBuilder forwardingOriginal(Email email);
```

`ReplyOptions` is an immutable core value with explicit `builder()`/`toBuilder()`, `defaults()` and accepted `allowUnencryptedContent()` factories. Its Builder owns `withQuotingTemplate(String)`, `resetQuotingTemplate()`, `withUnencryptedContentAllowed(boolean)`, `resetUnencryptedContentAllowed()`, explicit corresponding getters and `build()`. The immutable value exposes the same supplied choices via getters linked to setters. Default quote references `EmailStartingBuilder.DEFAULT_QUOTING_MARKUP`; permission defaults false. Required template rejects null before mutation. `ForwardOptions` has the analogous permission-only shape. No runtime crypto, settings/property/schema/EmailProperty/Spring surface is added for operation consent.

`ConfiguredEmailConverter.EmailConversion` adds `allowUnencryptedContent()`, `clearUnencryptedContentPermission()` and `isUnencryptedContentAllowed()`. Permission is local state on `FromEmail`; clearing restores the default false. It applies to every direct/result MIME/EML terminal, never changes the source draft and never bypasses configured encryption. The existing one-terminal conversion lifecycle remains; a fresh `fromEmail` starts without local consent. A failed terminal still consumes its source conversion under the established contract.

## Internal storage/assembly contract

Main-owned immutable serializable `ConfidentialContentState` contains the helper-derived component set (PLAIN_TEXT, HTML_TEXT, EMBEDDED_IMAGES, ATTACHMENTS, FORWARDED_MESSAGE) and deliberate draft permission. It contains no Email/parser/provider/private-key/stream references. InternalEmail and InternalEmailPopulatingBuilder expose it only internally. Old snapshots with no state mean no previously recorded helper requirement, not invented input evidence.

Copying the same draft preserves state. Explicit clears remove only the corresponding component; replacement/additive setters preserve it because content can still contain quoted material. New helper operations compute reused material from selected input facts plus any retained helper requirement, then apply their own options and never inherit an earlier operation's consent. A reply's generated alternative is confidential when derived from confidential source content; selected image occurrences count independently until explicitly removed. Format directives that include no source content (escaped percent/newline/non-null Boolean or zero precision) create no HTML quote obligation. An interpreted forward carries its material under FORWARDED_MESSAGE. Original forwarding adds the complete retained resource in its actual format without rendering edited content; missing complete retained input fails during preparation. Governance retains submitted obligations and adds obligations for actual selected template components, without importing template consent or received-field facts.

The final guard runs only after applicable outgoing choices have resolved and protection has completed. It receives local conversion consent explicitly; it does not mutate Email to communicate consent. Suitable successful enclosing encryption can cover an internally rendered forward. No signature-only state, encrypted sibling or ciphertext-inside-an-otherwise-plaintext payload supplies confidentiality for reused readable content. Guard failure is a preparation/conversion refusal; diagnostic terminals have no successful output and leave input Problems untouched.

Governance keeps provided source/Problems/originals and family history. `EmailConfigurationResolver.collectionSelection` records source role and ordinal at occurrence admission under the unchanged resolver precedence/dedup rules. `GovernedEmailInspection` restores only submitted-owned current facts: scalar/calendar selections by their actual selected declaration, unchanged aggregate recipient lists by submitted ordinal sequence, and resources/originals by exact admitted source positions. Equal-valued scalar overrides remain replacements; template values do not import received proof. Relevant forced lock choices remain caller-supplied, while unrelated lock-induced recipient rebuilding does not erase evidence. Exact-header associations remain authoritative through envelope-only locking; a changed envelope sender remains caller-owned. The existing direct DeliveryStatusReport completion behavior is unchanged; this work does not expand report projection.

## Header-role and private-header decisions

| Role | Ordinary read/copy | Reconstructed output / helper |
| --- | --- | --- |
| Subject, From, To/Cc/Bcc, Reply-To, Message-ID, Date | One typed authority, case-insensitive view, source raw fallback where interpretation failed | Typed values emitted once; a typed edit removes stale generic authority. Incompatible explicit reserved choices fail clearly. |
| References, In-Reply-To | Selected authored identity/header view; complete occurrence list | Preserve selected authored chain in a normal copy; a reply derives only selected logical ancestry. Generated carrier/adapter IDs never supply absence. |
| Return-Path | Readable actual received header plus normal Bounce-To interpretation | Do not emit old trace header; honor typed Bounce-To SMTP envelope. New helper leaves Bounce-To to caller/governance. |
| Received, Authentication-Results, Received-SPF, DKIM-Signature, ARC-* and delivery traces | Readable represented history with owner/source | Omit automatic current claims on rebuilt output; exact/original payloads retain bytes. Explicit incompatible attempts need role-specific handling rather than a global provenance gate. |
| MIME-Version, Content-Type, Content-Transfer-Encoding and producer structure headers | Preserve source evidence/read view as useful | Producer owns current structure/encoding; stale input cannot override. |
| Additional custom fields | Chosen authored complete list wins case-insensitively; retain occurrences | Emit appropriate fields in occurrence order; helper does not blanket-copy them to new outer message. |

Public subject selection is independent of consent: a confidential selected subject uses a positively established public counterpart for the same message; otherwise `Re: Your message` / `Fwd: Message`. Native cached/generated headers cannot prove that counterpart. Confidential logical threading cannot be exposed by assuming body encryption covers outer headers: omit private automatic ancestry from the new outer message unless a public same-message counterpart is positively established. An interpreted forwarded inner message is inside enclosing MIME-body encryption; an outer helper Subject stays safe.

References/In-Reply-To confidentiality is captured per selected name independently of Message-ID inspection. Replacing/clearing the ID alone never makes retained private ancestry public. Copies and snapshots preserve these internal markers; explicit generic list replacement clears that list's old association, append preserves prior confidential occurrences, and clearHeaders removes it. Governance propagates only the actual selected header list's marker. No new public threading selector/value model is added. Reply-image obligations likewise follow the actual selected CID occurrence's inspection, paired with its snapshot during helper assembly, including an ordinary attachment deliberately reused inline.

Original-payload coverage is captured internally as UNKNOWN / AS_RECEIVED / CONFIDENTIAL / INTACT_PROTECTED on the core immutable inspection snapshot, without a public mode/getter. AS_RECEIVED keeps actual root input before opening its protection. A plain EML/MSG child extracted under ancestor encryption is CONFIDENTIAL even though it is that child's complete original; body encryption alone does not protect its clear original headers. Only actual retained encryption covering the reused payload qualifies as INTACT_PROTECTED; signing/CONTENT_PROTECTED alone does not. Original forwarding sets an ATTACHMENTS reuse obligation for confidential plaintext originals and uses a neutral format-based carrier name with no inherited description/CID when confidentiality is established, sharing original payload storage. The original getter keeps its real metadata/bytes. Source edits, copying, completion and supported snapshots retain the historical coverage; output can use suitable encryption or conversion-local permission without a new original-forward overload. Ordinary plain originals remain unguarded controls, and a root encrypted original retains its unencrypted-outer path.

Original-file carriers use explicit base64 to preserve arbitrary captured bytes through ordinary SMTP DATA. EML/composite originals use application/octet-stream file transport with their actual-format filename; application media types such as native MSG/CMS remain their media types. This avoids illegal base64 message/rfc822 or multipart output and preserves bare-LF input without provider/global rewriting. The new carrier delegates the original read stream, owns only carrier metadata/encoding, and leaves historical original resource/type/bytes untouched. Interpreted forwarding retains its separate reconstructed MIME-message operation. See RFC 2046 sections 4.5.1 and 5.2.1 for the carrier/encoding distinction.

### Concrete emission/advanced-composition inventory

`OutgoingHeaderRoles` treats Subject, From, To, Cc, Bcc, Reply-To, Date and Message-ID as typed authorities; generic setters update the ordinary typed values, and current MIME emits each once. The producer owns MIME-Version, Content-Type, Content-Transfer-Encoding and Content-Length; omitted producer-owned fields are not forced into the output. Received delivery/authentication history names are Return-Path, Received, Authentication-Results, Received-SPF, DKIM-Signature, DomainKey-Signature, ARC-Authentication-Results, ARC-Message-Signature, ARC-Seal, Delivered-To, X-Original-To, Envelope-To, X-Envelope-To and X-Envelope-From. These remain readable on imported/copied Email values and are omitted on reconstruction. Explicitly supplying one of those producer/history names as a current generic claim fails clearly at reconstructed output, rather than silently discarding an application choice. Use content/body/resource/encoding APIs, typed Bounce-To, or explicit exact/original preservation respectively. This is a per-header role rule on all Emails, with per-name explicit intent; no general parsed/composed activation gate is introduced.

The full `MessageHeader` inventory also classifies Content-MD5, root Content-Disposition/Content-ID/Content-Description/Content-Base/Content-Location and legacy resource-parameter names size/filename/name as producer-owned; Resent-Date/From/Sender/To/Cc/Bcc/Message-ID, Status and Errors-To are history/envelope claims. Imported values remain readable and are omitted; explicit incompatible choices fail clearly. The parser placeholder ':' cannot be an output field. Sender, Comments and Keywords retain useful advanced composition: only actual selected explicit per-name choices emit them, while imported copies retain readable history. References, In-Reply-To and additional custom names retain their ordinary additional-header roles. When typed disposition/return-receipt notification is active it emits that header once; otherwise its additional raw representation retains the established route. Governance derives explicit intent from each name's actual selected source, honoring exclusions and losing declarations. Per-name occurrence order is preserved. Exact relay and original retained payloads bypass reconstruction and remain byte-authoritative.

The standalone `MailerHelper.signMessageWithDKIM` / `signAndOrEncryptMessageWithSmime` utilities remain configuration-only: their caller-supplied MimeMessage is the authoritative content, unrelated to any message content on their Email settings argument. They do not automatically reconstruct/include that Email's helper content. Applying its helper state as a new gate would falsely bind unrelated inputs and could undo deliberate conversion-handoff consent. Their existing requested-operation, missing-module, failure and no-op/no-content-read contracts therefore remain unchanged. Reconstructed FromEmail and actual draft sending/rehearsal paths enforce the safeguard before those artifacts can reach a utility.

The completed guard requires both successful requested encryption and an actual matching S/MIME enveloped-data or RFC 3156 OpenPGP encrypted MIME envelope, rather than accepting a signature or a custom Content-Type claim. A forward whose inner output was itself successfully encrypted needs no redundant outer-body protection for body-only obligations; confidential inner headers still require enclosing protection. Base-only rehearsal continues to describe unsecured preview bytes for ordinary inputs, but refuses unconsented helper reuse because those bytes leave the library. When a helper-required draft has encryption configured, even deliberate helper permission does not allow skipping that encryption in a returned base artifact; callers use secured rehearsal instead. Without configured encryption, deliberate helper permission can permit an unencrypted preview as it permits other finalized outputs.

## Representative behavior gates

Refuse final unencrypted MIME/EML/send/CustomMailer artifacts for confidential helper reuse, permit draft or one-conversion consent, and preserve source state after the latter. Inspect actual output for enclosing encryption and interpreted/original payload choice. Cover copies/snapshots, both body clears versus one body edit, image/forward clears, governance templates/overrides/locks, base rehearsal, static converter adapters, absent protection modules, no parsed/composed global gate, invalid encryption with consent, safe subjects and selected ancestry. Exact authoritative bytes/envelopes and plain/signature-only helpers are controls.
