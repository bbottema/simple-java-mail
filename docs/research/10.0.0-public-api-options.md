# Simple Java Mail 10.0.0 public API decision options

The everyday compose-and-send workflow still earns the name Simple Java Mail. The strongest improvements for 10.0.0 would make common operations more predictable, give failures and observation a coherent application contract, and contain advanced configuration without taking away capability.

This document covers every finding in the holistic API review, including the smaller consistency issues and README ordering. It offers alternatives and a recommended direction for discussion, one decision at a time. **Decisions 1 through 9, including their lettered subitems, and decisions 11 through 13 have accepted choices recorded below. The status table records completed implementation and release-tracked work. Decision 10 is parked. Decision 13's README overhaul and final website review are tracked in readiness issue #767 for completion before publishing 10.0.0.**

Initial review baseline: 20 October 2026, `codex/10.0.0` at `69c483280394a743b5b73312ed0fcfc3dfd972d5`. Library sources were unchanged at that baseline; the README and other documentation contained ongoing work. The problem statements describe that initial source review. API sketches began as proposals; the individual decision statuses and verification records below identify the final implemented choices.

## Principles shared by the options

- Preserve the factory, immutable snapshots, reusable Mailers, explicit execution views and ordinary fluent composition.
- Preserve the established set/clear/reset doctrine. Document which collection methods append and which methods replace their scoped value; copying retains the source values before subsequent operations.
- Keep SMTP acceptance, operation completion and mailbox delivery distinct. Cancellation and missing receipts cannot establish non-acceptance.
- Preserve caller ownership of executors, callbacks and external content. A simpler signature must not silently add eager attachment reads or resource ownership.
- Keep application contracts in core, implementations with their owning modules, and optional integration dependencies out of ordinary configuration contracts.
- Prefer one canonical route for each task. Decision 1 removes moved scalar methods in 10.0.0 without compatibility aliases; compatibility choices for the other decisions remain open.
- Distinguish released 9.x contracts from unreleased 10.0.0 additions before choosing removal, aliases or migration recipes. Source-compatible changes can still change behavior.

The existing [API workflow](../API_EXPANSION_WORKFLOW.md) and [ADR 0031](../adr/0031-public-api-and-internal-construction.md) govern implementation and module boundaries. Several options deliberately propose changes to accepted behavior; the affected ADRs are identified below.

## 1 Builder size and discoverability

The standard Mailer builder currently exposes 166 signatures across 161 names in the review's source count, excluding Object methods and the duplicate inherited build declaration. Inspection and clear/reset/restore companions account for 103 signatures. The Email composition builder has roughly 213 signatures. These counts describe discovery cost, not a target to minimize mechanically.

| Option | Approach | Benefit and cost |
| --- | --- | --- |
| A | Keep the flat API; improve Javadoc grouping, examples and IDE documentation. | Lowest migration cost. Does little to reduce the completion list or the number of concepts visible at once. |
| B | Keep common composition and SMTP setup direct; move cohesive advanced settings into immutable configuration groups. | Reduces the ordinary surface while retaining inspection and reset behavior within each group. Requires deliberate migration of existing methods. |
| C | Introduce a small basic builder and a separate advanced builder or view. | Strong separation initially. Users must cross another API boundary as requirements grow, and the two surfaces can drift. |

**Decision: B accepted, including the concrete groups below.** Keep `from`, `to`, body content, attachments, server setup and execution selection readily available. The existing debug, telemetry and retry values establish the pattern.

A group setter should replace the supplied group. Its unset fields resolve against the captured configuration, rather than accidentally retaining values from the previously supplied group. Group builders retain their own getters and clear/reset companions. Avoid a mutable callback DSL that lets a half-edited child configuration escape.

Proposed shape:

```java
mail.mailerBuilder()
    .withSMTPServer(host, port, user, password)
    .withConnectionPoolConfig(poolSettings)
    .withAsyncExecutionConfig(executionSettings)
    .buildMailer();
```

`ConnectionPoolClusterConfig` already represents overrides for a particular cluster. Reuse common setting definitions where useful, but preserve the distinction between Mailer defaults and cluster overrides. Do not repurpose that type merely because its fields look similar.

**Compatibility:** the direct conveniences retained below remain available. Remove moved scalar setters and their inspection/reset/clear companions in 10.0.0 without deprecated aliases; supply migration examples. Keep CLI scalar options through its existing internal adapters, and check Spring binding and property parity. Preserve existing fallback, explicit-disable and lock semantics during grouping; the broader vocabulary changes in item 7 remain a separate decision.

**Evidence to require:** ordinary sending remains equally short; grouped and scalar migration examples produce equivalent effective settings; getter/reset/lock behavior remains predictable; core-only and JPMS consumers compile.

Sources: [MailerGenericBuilder](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/MailerGenericBuilder.java), [EmailPopulatingBuilder](../../modules/core-module/src/main/java/org/simplejavamail/api/email/EmailPopulatingBuilder.java), [cluster settings](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/config/ConnectionPoolClusterConfig.java), [ADR 0031](../adr/0031-public-api-and-internal-construction.md).

### Accepted Mailer groups

Use immutable configuration values with explicit builders. Each group has one setter on the Mailer builder, with its detailed setting/getter/clear/reset methods on the group's own builder. Existing group names remain where they already describe a cohesive responsibility.

| Mailer builder method | Supplied value | Settings owned by the group |
| --- | --- | --- |
| `withConnectionPoolConfig(...)` | `ConnectionPoolConfig` | Core/max connections, claim timeout, idle and creation-age expiration, cluster key and load balancing. Share setting definitions with existing per-cluster overrides without erasing their different fallback scope. |
| `withAsyncExecutionConfig(...)` | `AsyncExecutionConfig` | Owned worker count and keep-alive, waiting queue capacity, and either `rejectWhenFull()` or `waitForCapacity(Duration)`; alternatively a caller-owned ExecutorService. Waiting for capacity occurs on the submitting thread. Custom-executor and built-in-worker settings have explicit applicability rules. |
| `withProxyConfig(...)` | `SocksProxyConfig` | SOCKS host/port, credentials and authenticated-proxy bridge port. This is supplied configuration; the existing ProxyConfig read contract continues to describe effective routing. |
| `withSendingLimitsConfig(...)` | `SendingLimitsConfig` | Message and recipient rate limits, their periods, allowance-sharing group and burst policy. Reuse SendingRateLimit as the count/period value. |
| `withConnectionConfig(...)` | `ConnectionConfig` | Socket timeout, local bind address/port, SMTP client hostname and legacy SMTP content compatibility. |
| `withTlsConfig(...)` | `TlsConfig` | Trust exceptions, server-identity checks, custom SSL factory and the existing opportunistic-upgrade customization. Keep the current TransportStrategy selector direct until decision 5 settles security/authentication separation. |
| `withValidationConfig(...)` | `ValidationConfig` | Address validator, blocking-versus-warning behavior and maximum prepared message size. |

Keep the existing cohesive retry policy, SessionDebugConfig, MailSendTelemetryConfig and MailSendHandlers as separate values. Their independent lifetimes and delivery contracts do not justify a combined diagnostics or monitoring configuration. Keep failover's destination/policy pair together through the existing operation.

Keep these direct on the ordinary Mailer builder:

- SMTP server setup and transport strategy selection, with its scalar setup conveniences.
- `withEmailDefaults(...)` and `withEmailOverrides(...)`, which already accept reusable Email templates.
- `withMailSendTimeout(...)`, because a total operation budget is distinct from socket, pool and queue limits.
- Group setters, their group-level inspection/restoration operations, and `buildMailer()`.
- Focused runtime integration hooks: custom sending, handler factory/ID generation and raw Jakarta Mail properties. Decision 4 can later refine invocation observation.

The grouped configuration must preserve the existing caller-supplied Session boundary. In particular, collecting TLS and connection settings must not silently start applying defaults to a Session that currently retains its own settings. Custom-factory choices retain an explicit supported construction scope.

Proposed usage:

```java
Mailer mailer = mail.mailerBuilder()
    .withSMTPServer(host, 587, user, password)
    .withTransportStrategy(TransportStrategy.SMTP_TLS)
    .withConnectionPoolConfig(ConnectionPoolConfig.builder()
        .withMaxSize(8)
        .withClaimTimeout(Duration.ofSeconds(5))
        .build())
    .withAsyncExecutionConfig(AsyncExecutionConfig.builder()
        .withThreadPoolSize(8)
        .withQueueCapacity(100)
        .rejectWhenFull()
        .build())
    .withMailSendTimeout(Duration.ofSeconds(30))
    .buildMailer();
```

The outer call names distinguish connection reuse from asynchronous execution. Configuring pool limits retains the optional batch-module's activation rules; constructing a configuration value starts no workers or connections.

### Accepted Email groups

Keep recipients, subject, text/HTML, calendars, headers, attachments, explicit embedded images, reply/bounce addresses and message/date fixing directly available. Keep the typed DKIM, S/MIME and OpenPGP signing/encryption operations direct: those already accept cohesive feature-specific values. Detailed key/file/algorithm choices belong on those values rather than in additional positional Email-builder overloads.

| Email builder method | Supplied value | Settings owned by the group |
| --- | --- | --- |
| `withImageResolutionConfig(...)` | `ImageResolutionConfig` | Automatic image resolution from files, classpath and URLs; base locations, containment permissions and failure policy. Explicitly attaching an embedded image stays direct. |
| `withContentEncodingConfig(...)` | `ContentEncodingConfig` | Default and text/HTML/calendar transfer encodings. Individual attachment encoding remains part of that resource's configuration. |
| `withTemplateOptions(...)` | `EmailTemplateOptions` | Global default/override suppression and per-property suppression sets. Exact meanings of clear/reset/disable remain subject to decision 7. |
| `withSmtpDeliveryOptions(...)` | `SmtpDeliveryOptions` | DSN return/notify choices, fixed ENVID, onward REQUIRETLS and recipient-rejection continuation. These transport-only choices can also serve the constrained exact-message builder; recipient-specific preferences remain on recipients. |

Keep client read-receipt requests distinct from SMTP delivery options. Preserve their ordinary direct conveniences initially. Likewise, no collection-wide attachments/recipients group is needed simply to shorten the root list; common content addition should remain easy to discover.

### Group replacement and inspection

Group values describe supplied choices and remain reusable. Supplying a second group replaces the first group's supplied choices; unset fields inherit the captured configuration rather than the previous group. Existing explicit disable and locked-value semantics must survive the move. Detailed vocabulary is still decision 7.

For example, a pool group built with only max size should retain an unset claim timeout on its supplied-value getter. The built Mailer exposes the effective resolved timeout through its configuration inspection. No inspection call should resolve a named Mailer or allocate runtime resources.

Once a scalar setting moves, move its inspection and reset/clear companions with it. Remove the old root methods in 10.0.0; do not add deprecated migration aliases. Keep CLI scalar options through internal adapters; grouping the Java API does not require a new CLI syntax.

For a full async queue, `rejectWhenFull()` rejects new work immediately. `waitForCapacity(Duration)` waits on the submitting thread for a free queue slot up to the given limit, then rejects if none becomes available. The Java API does not require callers to combine an overflow-policy enum with a separately applicable wait timeout. Existing textual properties and CLI inputs can retain their compatibility contracts through internal adaptation.

## 2a Single-mailbox parsing

`from("Alice <alice@example.org>")` parses a mailbox, whereas `to("Bob <bob@example.org>")` currently retains the full string as the address. This inconsistency exists even for one mailbox; it is separate from splitting multiple addresses. The downstream validation consequence needs a focused reproduction.

| Option | Approach | Benefit and cost |
| --- | --- | --- |
| A | Treat all common String arguments as bare addresses; require separate name/address arguments or a Recipient for named mailboxes. | A narrow, teachable contract. Removes existing convenience from `from` and makes imported mailbox strings less convenient. |
| B | Parse one mailbox consistently in `from`, `to`, `cc`, `bcc` and the corresponding reply/bounce conveniences. | Fits ordinary expectations and existing sender behavior. Requires careful handling of explicit names and malformed input. |
| C | Keep existing methods and introduce explicitly named parsed-mailbox methods. | Clear new names and little behavioral migration. Leaves the original asymmetry and adds another method family. |

**Decision: B accepted for Email builder conveniences only.** One mailbox string should have one interpretation across common Email conveniences. An explicit display name must remain authoritative. Recipient builder interfaces, implementations and existing parsing contracts remain outside the change.

Implementation and verification are complete under a different worker after the grouping migration's passing verification baseline and independent Javadoc preservation audit. The same worker completed the additive/copying documentation accepted in decision 2b and the exact-copy clarification in decision 6a. Its [checkpoint report](https://github.com/bbottema/simple-java-mail/blob/e3fbaf777082955e6ea3d387b245254996d49505/docs/plans/10.0.0-email-address-conveniences.md) records the Windows formatter recovery, focused checks, fresh packaged documentation and coverage boundaries. This checkpoint preceded the 3/8a implementation.

```java
emailBuilder
    .from("Alice <alice@example.org>")
    .to("Bob <bob@example.org>");
```

Both calls would produce the expected separate name/address values. Comma-separated input must not silently select its first mailbox or unexpectedly create several recipients. Keep multiple-address parsing behind the recipients API. Preserve the division between tolerant import and strict outgoing validation; do not add network or DNS checks to setters.

**Compatibility and evidence:** characterize named/unnamed Email convenience overloads, explicit-name precedence, quoted names containing commas, encoded words, malformed input and multiple-mailbox input. Test To/Cc/Bcc and Reply-To/Bounce-To together. Use an internal helper for Email conveniences without altering Recipient builder contracts; existing Recipient builder tests remain behavior controls.

Sources: [composition contract](../../modules/core-module/src/main/java/org/simplejavamail/api/email/EmailPopulatingBuilder.java), [composition implementation](../../modules/simple-java-mail/src/main/java/org/simplejavamail/email/internal/EmailPopulatingBuilderImpl.java), [ADR 0035](../adr/0035-tolerant-reading-and-strict-production.md).

### Accepted convenience shape and behavior

Keep the Email builder's existing public method names and signatures. Its convenience methods use one internal single-mailbox interpretation. No new public parsing method family is introduced, and there is no change to the Recipient builder API.

```java
emailBuilder
    .from("Sender <sender@example.org>")
    .to("Alice <alice@example.org>")
    .cc("Accounts", "Audit <audit@example.org>");
```

| Input to a singular convenience | Result |
| --- | --- |
| `"alice@example.org"` | Address alice@example.org with no display name. |
| `"Alice <alice@example.org>"` | Name Alice and address alice@example.org. |
| Name `"Accounts"`, mailbox `"Alice <alice@example.org>"` | Name Accounts and address alice@example.org. |
| Null or blank explicit name, mailbox `"Alice <alice@example.org>"` | Use the embedded name Alice. A bare address still produces no name. |
| A quoted name containing a comma | Parse it as one mailbox; do not split punctuation naively. |
| Input parsed as multiple mailboxes or an address group | Throw IllegalArgumentException with guidance to the plural recipients builder. Never select only the first mailbox. |
| Nonempty input that cannot be parsed as a mailbox, or yields no mailbox | Preserve its original address text for the configured send-time validator. Never invent an address or drop the value. |
| Null or empty required mailbox argument | Reject as a missing argument. Existing nullable clear operations remain separate. |

Apply the common interpretation to the Email builder's `from`, `to`, `cc`, `bcc`, reply/bounce addresses and receipt-request address conveniences, including equivalent InternetAddress overloads. A supplied explicit nonblank name wins over an embedded name in both representations.

Enforce single-mailbox cardinality at this Email convenience boundary. Internal parsing building blocks can be reused, but do not change `IRecipientBuilder`, `IRecipientsBuilder`, their specialized methods or the existing first-mailbox helper behavior as part of this decision. The earlier proposal to change those Recipient contracts was withdrawn after the user clarified the scope.

Already constructed Recipient values remain authoritative when supplied to an Email: do not reparse them or change their metadata. Existing collection behavior preserves order and duplicates. Multiple-address expansion remains available through the plural Recipient builder with its existing contract. Parsing neither validates deliverability nor performs DNS/network work. Send-time validation remains configurable and separate from the immediate structural argument checks above.

Scope this decision to interpretation. Decision 2b separately confirms that Reply-To calls remain additive.

## 2b Reply-To accumulation

`withReplyTo` appends recipients even though its contract says “Sets”. The additive behavior is consistent with the other additive address conveniences; the documentation must state it clearly, including when editing a copy that already contains reply destinations.

| Option | Approach | Benefit and cost |
| --- | --- | --- |
| A | Preserve append behavior, correct the Javadoc, and prominently show `clearReplyTo().withReplyTo(...)` for replacement. | Preserves the established additive address API and set/clear/reset doctrine. Clear examples make accumulation and replacement explicit. |
| B | Make `withReplyTo` replace and provide `addReplyTo` for accumulation. | Clear editing semantics and an explicit additive operation. Existing repeated calls can change behavior without a compiler error. |
| C | Preserve `withReplyTo` as an append alias and introduce `replaceReplyTo`. | Safer migration for existing calls. Retains an ambiguous name alongside two explicit ones. |

**Decision: A accepted.** Keep the existing additive API and behavior. Do not add `addReplyTo` or `replaceReplyTo`, and do not change `withReplyTo` into a replacing operation. The earlier recommendation B was rejected because it would make Reply-To inconsistent with the other additive address conveniences.

```java
mail.emailBuilder().copying(original)
    .clearReplyTo()                       // removes copied reply destinations
    .withReplyTo("support@example.org")   // appends the first replacement
    .withReplyTo("case-owner@example.org") // appends another
    .buildEmail();
```

Without the clear call, both supplied destinations would be added to the copied Reply-To list. The collection overload also appends; an empty collection adds nothing and does not clear existing values. Preserve order and duplicates according to the existing contracts.

Keep method-specific collection preconditions explicit: `withOverrideReceivers(empty)` retains its existing nonempty-input rejection. The Reply-To/ordinary-recipient empty no-op rule is not a universal rule for every collection argument.

Document each additive Email address overload explicitly: it adds to existing values, repeated calls accumulate, and replacement uses the corresponding clear operation before setting new values. Retain accurate replacement wording for scalar operations such as From and Bounce-To; this is not a claim that every address method is additive.

The `copying(...)` introductions and relevant overloads must explain that the new builder starts with the copied collections. Subsequent additive calls retain those copied entries unless explicitly cleared. Replacing scalar setters keep their existing behavior, and changes to the copy do not mutate the original Email. Preserve the existing metadata, borrowed-content, exact-message and protection caveats while adding these examples and cross-links.

**Implementation scope:** documentation only, combined with the follow-on decision 2a work so shared convenience Javadocs are edited once after the grouping checkpoint. Preserve runtime behavior and Recipient builder contracts. Validate the generated Javadocs and any affected CLI help; retain existing copying/addition behavior tests rather than adding tests that merely mirror prose.

Sources: [public Reply-To contract](../../modules/core-module/src/main/java/org/simplejavamail/api/email/EmailPopulatingBuilder.java), [append implementation](../../modules/simple-java-mail/src/main/java/org/simplejavamail/email/internal/EmailPopulatingBuilderImpl.java).

## 3 Operational failure contract

`MailSendException` covers selected send failures, but queue rejection extends `RejectedExecutionException`, and `EmailTooBigException` extends `RuntimeException` directly. Even `MailException` cannot catch every routine SJM-created operational failure.

| Option | Approach | Benefit and cost |
| --- | --- | --- |
| A | Preserve exception inheritance and add a supported failure classifier. | Retains existing catch behavior and original instances. Callers still need a broad catch followed by classification. |
| B | Bring SJM-created operational failures under `MailException`, with stable public categories and optional submission facts where applicable. | One useful library-specific catch and consistent inspection. Changes exception inheritance for rejection and size failures. |
| C | Add a non-throwing send API that always returns a success/failure outcome. | Convenient for workflows that treat failures as data. Creates another sending vocabulary and leaves the throwing API to maintain. |

**Decision: B accepted, including the usage and inspection API below.** Reuse the existing root. Cover validation, size limits, execution admission, connection establishment, submission, cancellation, deadlines and cleanup. Retain distinct subclasses where they have useful additional facts, and expose a small typed category such as validation, capacity, connection or submission through the common contract. Category alone must never determine retry safety.

```java
try {
    mailer.sync().sendMail(email);
} catch (MailException failure) {
    handleOperationalFailure(failure.getKind(), failure);
}
```

Normalize a library-produced failure once so the caller and observer receive the same object. Preserve the provider cause and captured receipt. An accepted receipt followed by cleanup failure remains a failed operation with known acceptance.

The common MailException base exposes `getKind()`, `getSubmissionReceipt()` returning Optional and the ordinary `getCause()` contract. Receipt inspection requires no cast to MailSendException. Before receipt-producing work, the Optional is empty; absence does not establish rejection. Choose complete, stable category values after inventorying the owned failure paths.

Specific handling remains ordinary Java catch ordering:

```java
try {
    mailer.sync().sendMail(email);
} catch (MailSendRejectedException failure) {
    scheduleForLater(email);
} catch (EmailTooBigException failure) {
    reportMessageTooLarge(failure);
} catch (MailException failure) {
    failure.getSubmissionReceipt().ifPresent(this::recordSubmission);
    reportFailure(failure);
}
```

Implementation and verification are complete under a separate worker after grouping, the independent Javadoc preservation audit and the 2a/2b checkpoint. Decision 8a shared this owner because it touches the same receipt and failure-inspection contracts. The [checkpoint ledger](https://github.com/bbottema/simple-java-mail/blob/e3fbaf777082955e6ea3d387b245254996d49505/docs/plans/10.0.0-common-failure-contract.md) records library/consumer checks, fresh public artifacts, website examples and source/index preservation, including the controlled CLI cache-write recovery. Changed catch reachability and exception inheritance remain conditional/report-only migration cases wherever preservation cannot be established. Local Maven calls use `-Dlicense.skip=true`; implementation then continued with decision 5.

This contract should cover failures owned by SJM. Programmer errors and arbitrary exceptions thrown by application callbacks retain their documented behavior; do not turn every Throwable into an operational mail failure. Async completion retains ordinary CompletionException/ExecutionException wrapping at the Java future boundary.

**Compatibility:** `MailSendRejectedException` cannot simultaneously extend `RejectedExecutionException` and `MailException`. Existing rejection catches need a migration example. Public validation contracts should live in core-owned API packages; moving only some types into core's copy of an existing main-module package would create a JPMS split package. Resolve package placement explicitly.

**Evidence to require:** one catch handles all SJM-created categories in sync and unwrapped async paths; observer failure identity and receipts survive; callback-originated exceptions retain the promised identity. Revisit [ADR 0011](../adr/0011-transport-neutral-submission-outcomes.md) and [ADR 0012](../adr/0012-terminal-send-observation.md).

Sources: [MailException](../../modules/core-module/src/main/java/org/simplejavamail/MailException.java), [MailSendException](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/MailSendException.java), [queue rejection](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/MailSendRejectedException.java), [size rejection](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/EmailTooBigException.java).

## 4 Observation of a particular invocation

The per-send handler factory deliberately keeps handler/options parameters out of the send methods, avoiding overload growth across sync, async, retained connections and other applicable entrypoints. Applications still own the association between a business job and its observations. The remaining ergonomic question is whether that association is documented clearly enough; its existence does not by itself justify another sending API.

| Option | Approach | Benefit and cost |
| --- | --- | --- |
| A | Enrich the factory input with a typed invocation descriptor. | Viable without send overload growth when concrete SJM-provided information is missing. Message metadata alone cannot supply business context specific to an invocation. Remains available but unselected. |
| B | Add overloads accepting MailSendHandlers at the send invocation. | Direct context capture, but reintroduces the send-options method proliferation the factory was designed to avoid. Recommendation withdrawn after the user's design clarification. |
| C | Introduce a fluent send-request object that collects context, handlers and options before sync or async execution. | Strong setup boundary and room for future options. Adds another object and another way to initiate a send. |
| D | Retain the existing factory and document a concrete application-context capture and correlation pattern. | Preserves the intended API and handler lifecycle, with explicit application ownership of business context. Accepted. |

**Decision: D accepted.** Retain the existing factory and sending methods. Explain how an application captures a snapshot of its business context when the factory creates the handlers. The closure then carries that context through later progress and result callbacks without consulting the callback thread's ambient context. Original option A remains a viable alternative if a concrete need for richer factory input is established; it is not part of this accepted change. Documentation-only work is a separate option rather than a relabelling of A.

```java
mailerBuilder.withSendHandlersFactory(observationId -> {
    String jobId = jobContext.currentJobId();
    return MailSendHandlers.builder()
        .withProgressObserver(progress -> jobs.showProgress(jobId, progress))
        .withResultObserver(outcome -> jobs.recordOutcome(jobId, outcome))
        .build();
});
```

Here `jobContext` and `jobs` are application-owned collaborators. For individual sends the factory runs on the invoking thread before preparation/admission, so capture the business context there. Do not imply that a ThreadLocal read performed later inside an observer runs on that same thread. The existing inline-result-callback contract makes `recordOutcome` part of completion latency; applications can select a borrowed executor when appropriate, with the existing handoff limitations.

## 12 Configuration property typing

`<T> T getProperty(Property)` infers T from the caller rather than the key. `String port = config.getProperty(SMTP_PORT)` therefore compiles and can fail at runtime. Existing typed-name getters also accept any Property enum value. Duration representation differs between property families.

| Option | Approach | Benefit and cost |
| --- | --- | --- |
| A | Make dynamic access explicit with Object values or a requested Class checked against the schema. | Honest runtime typing and relatively small migration. Invalid key/type combinations still compile. |
| B | Introduce schema-backed ConfigKey<T> values and make typed reads accept those keys. | The compiler rejects mismatched reads. Requires typed key definitions and migration of generic accessors. |
| C | Expose only cohesive typed configuration views and reserve dynamic maps for diagnostics/integration. | Strong domain structure and good completion. Can duplicate the builder/effective configuration model and limit generic tooling. |

**Decision: B accepted; implemented and verified.** The catalogue binds all 111 properties directly to typed parser/projection factories, with no parallel type table. Compilation controls accept valid reads/fallbacks and reject wrong scalar/map targets, wrong explicit/fallback values, the old unsafe getter families and caller-created keys. Real JDK 11 passes 52 core and 284 main cases; real JDK 17 passes 91 CLI and 50 Spring/starter cases. Fresh Javadocs, rendered website examples, genuine metadata generation, final packaged API/distribution/help on JDK 17/21 and source preservation pass. All original staged entries remain; one unrelated post-entry staged close-ledger addition is preserved rather than undone or misreported as byte-equal to the earlier snapshot. The worker released the source/build slot to final documentation decision 7. See the [implementation ledger](https://github.com/bbottema/simple-java-mail/blob/e3fbaf777082955e6ea3d387b245254996d49505/docs/plans/10.0.0-typed-configuration-keys.md) for exact evidence and coverage limits. Properties are first-class configuration values, so their keys should also carry their value types. Introduce schema-backed `ConfigKey<T>` values exposed through `ConfigKeys`, and make typed reads accept those keys. Derive key types and parsers from one schema so they cannot drift apart. An enum cannot assign a different generic parameter to each constant, so this requires a typed key abstraction rather than a cosmetic change to Property. Ordinary reads must reject mismatched key/value types at compile time rather than merely checking a caller-supplied class at runtime.

```java
Integer port = config.get(ConfigKeys.SMTP_PORT);
Duration timeout = config.get(ConfigKeys.SESSION_TIMEOUT);
// String port = config.get(ConfigKeys.SMTP_PORT); would not compile.
```

Align `valueOrProperty` with the same typed key; otherwise the unsafe path remains. Use one canonical typed read route rather than adding parallel getter families. Expose time-valued Java reads as Duration while preserving existing configuration-file units, range constraints and parsing rules. Preserve nullable absent scalar values, explicit-value/configured-value/fallback precedence, detached immutable snapshots, named-configuration isolation and locks. Dynamic maps remain explicitly heterogeneous, and safe diagnostics remain the route for logging values and provenance.

Configuration snapshots contain only explicitly configured values: absent aggregate properties (extra properties, pool clusters and named mailers) retain their existing nullable read contract, with detached immutable typed maps when present. Decision 9's outgoing-operation collection convention does not fabricate configured empty maps here. Retain the parsed/raw representation where required for lock comparison, provenance and source-map round trips; schema-bound key projections can provide canonical Duration reads without changing textual units or parsing limits.

**Compatibility and evidence:** retain old textual property names and named-configuration isolation. Inventory released static ConfigLoader reads separately from the new snapshot API before deciding whether the old Property enum remains a parser compatibility surface. Test negative compilation for key/type mismatches, including `valueOrProperty`, duration conversion and overflow, absent values, redaction, source precedence and locked values. Coordinate type ownership with [ADR 0003](../adr/0003-immutable-configuration-snapshots.md), [ADR 0004](../adr/0004-configuration-provenance-diagnostics.md) and item 1. Include factual Javadoc preservation, normal website property examples and both OpenRewrite research/plan updates. Migration notes contain only demonstrated breaking changes or changed behavior against released APIs, not a tour of new typed keys.
