# SJM 10.0.0 migration tooling: implementation plan

Date: 2026-10-19. Status: proposed; no production recipes, report companion, or validation fixtures are implemented by this document.
The [research](10.0.0-openrewrite-migration-research.md) owns the evidence, alternatives, tool-distribution findings,
and the complete 39-topic migration inventory. This document owns scope, implementation order, and release acceptance.

## First useful release

Deliver a Java/Maven migration tool that can remove common 9.x compilation blockers, show a reviewable patch, and
produce a source-preserving report of application decisions and runtime checks. An application with unusual
configuration or lifecycle requirements must still receive useful findings when no source rewrite is appropriate.

The first release has three deliverables:

1. **Recipe library:** proposed artifact `org.simplejavamail:rewrite-simple-java-mail`, independently versioned from SJM,
   with public composites `org.simplejavamail.rewrite.MigrateToSjm10` and
   `org.simplejavamail.rewrite.ReviewSjm10Migration`.
2. **Report companion:** proposed executable artifact `org.simplejavamail:sjm-migration-report`, released at the same
   tooling version. It reads exported tables and writes `migration-report.md` and `migration-report.json`.
3. **Validation corpus:** real released-input projects, expected transformed projects, report expectations, and
   behavioral controls. These are development/CI assets, not application runtime dependencies.

Coordinates and names above are proposals, not published artifacts or commands users can run today. A separate
`rewrite-simple-java-mail` repository is the recommended eventual home. This plan does not create that repository.
Publish the first supported tooling release against a fixed SJM 10.0.0 release candidate or final artifact; label
candidate-only compatibility explicitly and revalidate before advertising final 10.0.0 support.

### Supported envelope

| Dimension | First release contract |
| --- | --- |
| Source | Released SJM 9.x Java APIs present in the versioned rule manifest. Run full fixtures at 9.0.0, 9.1.0, and 9.3.6; inspect intermediate release API surfaces before claiming the whole range. Otherwise publish the exact validated version list. |
| Target | One immutable 10.0.0 candidate/final artifact set, with coordinates, hashes and source provenance. Never silently build recipes against a changing developer installation. |
| Build | Maven single-module and reactor projects, including an inherited/managed SJM version. Support ordinary Java source/test source and an explicit dependency-module allowlist. |
| Runner | Initially pin the demonstrated Maven 3.9.10 / OpenRewrite plugin 6.46.1 / rewrite-core 8.89.0 combination. Test the runner on JDK 17 and 21. Keep recipe-authoring JDK requirements separate from consumer source level and SJM's Java 11 runtime minimum. |
| Java baseline | Parse representative Java 8 and 11 input; compile target fixtures with release 11 and run on 11, 17 and 21 where the SJM target supports them. CLI fixtures use Java 17 or newer. The OpenRewrite runner need not run on the application's oldest JVM. |
| Config/resources | Read recognized SJM properties, Spring configuration and CLI occurrences for evidence. No configuration-file, deployment-JVM, or CLI command rewrite in this release. List scanned paths and exclusions. |
| Other environments | Gradle, Kotlin and Groovy are explicitly unvalidated in the first release and must be shown as unsupported scope. Their acceptance work belongs to **Wider support**. |

Maven-first is deliberate: it is the end-to-end runtime established by the research. Gradle metadata availability
does not establish an equivalent working or anonymously resolvable toolchain. Do not make untested support a launch claim.

### User workflow

1. Build/test the application on its existing 9.x dependencies. Resolve its real source version and active Maven
   modules/profiles. Record a source-control baseline and the tool/target versions.
2. Run `ReviewSjm10Migration` on the old classpath with data-table export enabled. Render the report, including analysis
   gaps and project-level runtime checks. A missing classpath or failed parser is an actionable result.
3. Choose factory and execution-mode policy for an explicit module/source scope. Without a choice, affected sites
   remain unchanged and carry a decision finding; unambiguous type/literal rules can still run.
4. Dry-run `MigrateToSjm10`, producing a patch and report. Parse the input using the old dependencies. Plan source
   changes before dependency edits; do not upgrade dependencies and then try to parse removed APIs from scratch.
5. Apply the same configured recipe set, inspect the patch, then compile/test against the target dependencies.
   Application owners complete the report's decisions and runtime checks. The tool does not auto-approve them.
6. Re-run to establish idempotence and detect remaining statically visible old API use. Keep the baseline report:
   disappearing old syntax must not erase a pending runtime or lifecycle review.

The published README must contain copyable, pinned Maven commands for report, dry run, apply, and companion rendering,
including a Windows/PowerShell form with quoted `-Dkey=value` arguments. Integration tests must execute those exact
examples. The report-only command must not require enabling the mutating composite.

## Transformation contract

Each rule has a stable ID, exact old symbol/signature and source-version range, target signature, required policy,
guide topic, and positive/negative fixture IDs. Missing attribution is a reason to skip and report, never a reason
to fall back to text replacement. Public recipe descriptions must state these boundaries.

| ID / recipe responsibility | Included transformation | Preconditions and fallback |
| --- | --- | --- |
| SJM10-T001 / `MoveEmailProperty` | Move the exact enum type from `internal.config` to `api.email`; update qualified uses, imports and static imports. | Leave same-named application types untouched. Keep all enum values and exclusions unchanged. Link report topic R025 where suppression intent also needs review. |
| SJM10-T002 / `RenameScopedReceiptSend` | Rename `MailSender.sendMailAndGetReceipt(Email)` to `sendMail(Email)`. | Initially support direct calls on the typed sender supplied by a library `withOpenConnection` callback. Reject custom implementations, declarations, escaping senders, and unknown receivers. Top-level `Mailer` calls are a different rule and remain report-only. |
| SJM10-T003 / `UseDsnEnums` | Replace recognized String literals in the removed notify/return-option overloads with their parsed enum equivalents. | Support the exact released `withDeliveryStatusNotificationNotifyOptions(String)` and `withDeliveryStatusNotificationReturnOption(String)` signatures. Use old parser semantics for aliases/order. Dynamic values, null, invalid/empty literals and other overloads stay unchanged with R022 findings. |
| SJM10-T004 / `UseFactoryBuilderStarters` | Rewrite all 14 EmailBuilder and 16 MailerBuilder starter overloads to the chosen `SimpleJavaMail` factory. | Require accepted factory policy and exact overload attribution. Include the special `usingSession(session)` mapping. Coordinate with T005 and defer an initializer if its declaration/contract cannot accept the public return type. Support direct invocations first; method references, subclassing and unproved evaluation-order cases report R002. |
| SJM10-T005 / `UsePublicBuilderContracts` | Change simple local implementation-typed builder declarations to their corresponding public interfaces; replace simple recipient-builder construction through the chosen factory. | Require a non-escaping local, no reassignment to other implementations, and only public-contract uses. No fields, public signatures, subclass constructors or implementation-specific methods. Keep the declaration and initializer changes atomic. |
| SJM10-T006 / `MakeLiteralExecutionModeExplicit` | Select sync/async for explicit literal-boolean send, simple-batch and connection-test calls whose result is discarded. | Require an opted-in scope, a proven library-created non-null receiver, and a supported single-evaluation pattern. Preserve explicit true/false intent. Stored/returned/chained futures, nonliteral flags, no-flag calls and custom Mailers report R023/R034/R036. |
| SJM10-T007 / `AlignSjmDependencies` | Align allowlisted SJM application modules to the selected target in supported Maven declarations or a single unambiguous version property. | Preserve scopes, exclusions and management. Unknown imported BOM ownership, mixed SJM versions, unrelated consumers of a shared property, or unsupported declarations need a build finding. Do not rewrite all `org.simplejavamail` artifacts indiscriminately. |
| SJM10-T008 / `SetJavaBaseline` | Optional change to a recognized Maven compiler release/source-target setting or dedicated version property. | Disabled by default. Require explicit acceptance of Java 11 for libraries or Java 17 for CLI use. Conflicting profiles/toolchains/shared properties are reported. Never claim the deployment runtime was upgraded. |

These eight responsibilities constitute first-release scope. No other rewrite may enter the composite without a
manifest entry, fixture coverage, and an updated contract. Builder and send rewrites can change behavior in the ways
already explained by the migration guide; their reports must retain the related behavioral review items.

### Policy options

| Option | Required behavior |
| --- | --- |
| `targetVersion` | Required; must match the release manifest's validated target. Do not silently pick latest or a local SNAPSHOT. |
| Source scope | Resolve Maven modules and source-path globs explicitly. Log the scope in the report. Choices for one module must not become assumptions about another. |
| `factoryMode=review` | Default. Report factory-dependent changes without inserting a configuration source. |
| `factoryMode=conventional-defaults` | Use `SimpleJavaMail.fromDefaults()` within the accepted scope. Explain its shared lazy snapshot and flag observed global reload/mutation for review. Do not synthesize an application singleton or bean. |
| `factoryMode=existing-reference` | Require a configured local identifier or `this.field`, resolved at every site to an accessible `SimpleJavaMail`. Reject arbitrary code strings, calls, shadowed/wrong types, and unavailable references. The application accepts the chosen factory's configuration policy; the recipe verifies syntax/type/scope and conservative null/evaluation conditions. |
| `executionMode=review` | Default. No send-mode transformations. |
| `executionMode=literal-only` | Allow T006 in the selected scope; preserve explicit old boolean intent and emit the associated preparation/control review. No default mode is inferred for injected Mailers or no-flag calls. |
| `upgradeJavaBaseline=false` | Default. Emit the baseline decision. An explicit true only permits the narrow T008 build change. |

Do not insert a new `.sync()`/`.async()` receiver call before side-effecting arguments unless the supported pattern
and fixtures establish the intended evaluation order. The first release can reject a case rather than introduce
temporary variables or expand control flow. The same caution applies to moving factory initialization before arguments.
Static method references are excluded from factory rewriting until their initialization timing has a dedicated rule.

### Explicit first-release exclusions

- `shutdownConnectionPool()` renaming and adding/blocking close: report final-shutdown and drain ownership.
- Future-to-`MailSend` wrappers, cancellation adapters, public return-type changes, and no-flag mode inference.
- Removing builder `.async()` while dependent operations still need a decision.
- Rebuilding static configuration as DI/application factories, global reloads, or Spring bean redesign.
- DKIM default/override template conversion, security fallback changes, and automatic suppression of SMTP checks.
- Direct `Email` construction, result/exception construction, custom implementation migration, and serialization repair.
- Adding Angus/JPMS dependencies from incomplete evidence or changing provider-specific delivery code.
- Updating raw MIME goldens, clearing recipient overrides, or normalizing invalid configuration just to make tests pass.

Every exclusion must yield a concrete source finding when detectable, or an explicitly scoped checklist item where
the evidence is external. An exclusion is not permission to silently ignore the topic.

## Implementation structure and ownership

Use one independently versioned repository with the following responsibilities; exact directory names can follow
the OpenRewrite recipe-library template when implementation begins.

| Component | Owns | Must not own |
| --- | --- | --- |
| `recipe` artifact | Public composites, typed Java visitors, Maven changes, options and preconditions. | Application runtime configuration, network SMTP activity, or report presentation. |
| `analysis` package within the recipe artifact | Per-run scan accumulator, symbol/version resolution, bounded local ownership facts, coverage accounting. | Global mutable caches, cross-run application state, or whole-program certainty claims. |
| Versioned rule manifest resource | Stable T/R IDs; old/target signatures; supported versions; policy; guide anchors; detector/checklist classification; fixture references. | A second copy of migration prose that drifts from the guide. |
| Report tables in the recipe artifact | Schema-versioned findings, run metadata and analysis-coverage rows. | Source markers or edits in report-only mode. |
| `report-cli` artifact | Read one explicit run's tables, normalize paths/statuses, render JSON/Markdown, apply requested exit policy. | Re-running Maven, resolving application classes, or changing source/build files. |
| `validation-fixtures` and CI harness | Isolated input/output builds, semantic controls, snapshots, tool-distribution checks and release gate. | Publishing application dependencies or editing the SJM checkout under test. |

Use built-in `ChangeType`/`ChangeMethodName` behind appropriate preconditions where they fit. Use custom visitors for
DSN arguments, factory chains, mode calls and report-only scanning. Use a scanning recipe where ownership facts must
be gathered before a rewrite. Restrict all accumulator state to a run and module; fixture parallelism must not leak policy.

Keep old and target symbols available for recipe authoring without putting two incompatible SJM versions on the
consumer application classpath. Generate/use versioned type tables or parser resources for attribution and JavaTemplate
construction; target API classes are not production runtime dependencies of the recipe artifact. Follow OpenRewrite's
[multiple-version guidance](https://docs.openrewrite.org/authoring-recipes/multiple-versions) and
[recipe test guidance](https://docs.openrewrite.org/authoring-recipes/recipe-testing).
Do not disable type validation to hide a failing generated tree.

Use JDK 21 to author/build the tooling while compiling its production bytecode for the declared JDK 17 runner floor.
Test the packaged recipe and companion on JDK 17, not just the authoring JVM, to catch accidental linkage to newer APIs.

The composite must collect baseline findings before mutating source/build declarations. Verify the ordering with the
pinned runtime: subsequent cycles, generated target types, and Maven model refresh must not lose old-symbol matches
or generate duplicate findings. A fresh application compilation is a separate process against target dependencies.

## Report companion specification

### Tables and schema

Provide three custom data tables, exported using stock OpenRewrite facilities:

| Table | Required fields |
| --- | --- |
| `SjmMigrationRun` | Schema/tool versions, run ID, review/dry-run/apply mode, source version per module, target version/hash, plugin/core/JDK versions, active modules/profiles and sanitized policy selections. |
| `SjmMigrationFindings` | Stable rule ID, topic ID, module, normalized repository-relative path or module scope, line/column when available, enclosing symbol, evidence kind, status, concise reason, required action, guide URL, stable fingerprint. |
| `SjmMigrationCoverage` | Module/language/source-set and recognized resource scope, candidate/analyzed/excluded/unparsed counts, attribution failures, unsupported-version/language/build reasons, and each topic's detector versus checklist coverage. |

Include enough run metadata to detect missing tables and incompatible schemas. No table rows may contain passwords,
tokens, raw configuration values, arbitrary Java argument literals, full source lines, or machine-specific absolute
paths. Use symbols and redacted evidence labels. Format CSV correctly for commas, quotes and newlines, and prevent
spreadsheet-formula interpretation of attacker-controlled text fields in exported views.

Status vocabulary:

- `change-proposed`: dry-run patch contains this supported transformation.
- `change-applied`: apply execution recorded this transformation; target compilation remains a separate check.
- `decision-needed`: source/build evidence requires an application choice or unsupported edit.
- `runtime-review`: a behavior must be validated against application data, environment, or lifecycle.
- `unanalysed`: the requested scope could not be assessed reliably.

Use confidence/evidence kinds such as `typed-match`, `literal-config`, `bounded-flow`, and `project-checklist`.
A project checklist must not pretend to be a line-specific defect. Record an unavailable position explicitly rather
than assigning a misleading line. Keep column/line acquisition independent of formatting changes.

Fingerprints combine stable rule/topic ID, module, normalized path, enclosing symbol and normalized occurrence
context; exclude line number, timestamps and secret values. Deduplicate across cycles without collapsing distinct
call sites. Preserve all reasons when several topics apply to one site. Establish this behavior with fixtures before
introducing a persistent acknowledgment ledger.

### Human-facing output

The Markdown report starts with the tool/target/source versions and a coverage summary. It then lists:

1. Unanalysed scope and decisions blocking compilation or policy selection.
2. Proposed/applied source changes with links to the diff and source locations.
3. Behavioral/runtime checks grouped by migration topic with direct guide links.
4. Unsupported/excluded scope and the exact commands/versions used to produce the report.

Each finding must answer: what was found, why it matters, what the owner should do, and where the explanation lives.
The first release needs Markdown and JSON only; HTML is a later renderer. Include the report in generated build
output (`target/sjm-migration/<run-id>/`), not among the application's tracked sources by default.

The companion takes an explicit table/run directory and output directory. It must not guess the newest timestamped
directory and accidentally combine separate runs or modules. Integration tests will establish how Maven reactor
outputs are aggregated and associated with one run.

Use these exit-code semantics:

| Exit code | Meaning |
| --- | --- |
| 0 | Valid report produced; this alone does not mean the migration is complete. |
| 1 | Invalid/missing input, unsupported schema, inconsistent run metadata, or report-generation failure. |
| 2 | An explicitly requested finding gate matched unresolved statuses. |

The optional gate accepts a list of statuses, for example `decision-needed,unanalysed`; a user may include
`runtime-review` if every runtime checklist must be closed elsewhere before CI passes. Do not reuse Maven's
`failOnDryRunResults` as a finding gate: table-only findings can exist without a diff.

### Review-only guarantees

`ReviewSjm10Migration` returns the original source/build trees and exports tables only. Hash all input source,
resource and build files before and after the integration test. Build-directory output is allowed; tracked file
changes and `SearchResult` markers are not. Validate parser/error cases as well as successful matches.

Keep baseline and follow-up reports separate and reference the baseline from the follow-up. A finding may disappear
because its old API was changed; that does not automatically resolve a runtime review. The first release leaves
acknowledgments with the application owner. A machine-managed ledger and cross-run reconciliation belong to Broader coverage.

## Validation fixtures

### Corpus layout and execution

Store each case with an ID, source SJM version, target artifact identity, policy, input sources/build files, expected
patch or unchanged files, expected findings/coverage, and the assertion being tested. Keep source snippets small
enough to explain a rule. Also keep complete Maven projects to catch classpath, packaging and reactor errors that
snippet tests miss.

For every transforming rule, run these distinct checks:

1. Compile the untouched input against the real supported 9.x artifact in an isolated workspace/cache.
2. Run RewriteTest before/after and negative cases with type validation enabled; assert a subsequent recipe cycle
   makes no additional change.
3. Execute the published Maven invocation on the input project, inspect patch/report expectations, and apply.
4. Compile the actual transformed project against the frozen target artifact in a separate process. Resolve target
   artifacts by the recorded identity, not by whatever is installed in the developer's Maven repository.
5. Run a second full invocation and assert an empty source/build diff, no duplicated report rows, and accurate scope.
6. Run the relevant behavioral assertion when the transformation touches evaluation, configuration or execution.

Expected output compilation is not sufficient: the harness must compile the output actually produced by the recipe.
Keep released-input and target-output classpaths separate. API-only scans of other 9.x releases supplement these
fixtures; they do not substitute for the representative end-to-end builds.

Successful target compilation is required for fixtures that claim a complete supported migration. Negative fixtures
must compile as released input, remain unchanged at the unsupported site, and emit the specified finding; they may
still fail against 10.0.0 until an application decision is applied. Mixed supported/unsupported fixtures must label
that partial result explicitly. Do not make a test pass by deleting the unsupported site or claiming its target build
succeeded. Already-invalid input belongs to the incomplete-analysis corpus with the original failure recorded.

### Behavioral controls

These tests define the semantic boundary of the tool. Some confirm an accepted transformation; others prove why the
first release leaves a case for review.

| Control | Required assertion |
| --- | --- |
| Evaluation order | Counter/logging arguments and null receivers show single evaluation and exception order. A rejected pattern remains unchanged; a supported pattern preserves its promised order. |
| Conventional factory | Separate JVMs with synthetic properties/environment/system values verify the target's shared lazy snapshot and precedence. Global reload cases are detected rather than claimed equivalent. No test reads the maintainer's real mail credentials or contacts. |
| Existing factory | Two distinguishable factory configurations demonstrate that rewrites use the explicitly selected local/field factory, without accidentally falling back to conventional defaults. |
| Async preparation | Controlled validators/attachments establish the 9.0.0 versus 9.3.6 versus target timing/failure differences. Reports retain R034 after a mode rewrite. Accepted behavior is stated explicitly; equivalence is not asserted where the library intentionally changed it. |
| DSN | Compare literal parsing and target enum state, including aliases and duplicates. A local scripted SMTP server can inspect envelope commands where a delivery assertion is required. Do not send external email. |
| Lifecycle and cancellation | Controlled executors/latches demonstrate drain and detached-completion behavior; verify that excluded adaptations are reported and unchanged. No sleeps as the primary race assertion. |
| Runtime review examples | Representative SMTP capability/SIZE, copied test-inbox overrides, attachment closing, encoded EML and finalized MIME cases show why compilation cannot close R007/R008/R027/R028/R038/R039. Retain these as explanatory fixtures without rewriting their golden expectations automatically. |

The migration-tool corpus is not a duplicate of SJM's complete test suite. Use minimal contracts and targeted controls;
link to the SJM behavior under test where useful. Network fixtures must use loopback and deterministic local servers.

W0 must capture uncommitted SJM/website provenance if a candidate is built before source commits exist: include a
content manifest and resulting artifact hashes in an isolated snapshot. A HEAD SHA alone is insufficient. Follow the
repository's normal release/build procedures; tooling development must not change SJM versions or publish its release.

### Definition of done for the first release

- [ ] Every T rule has exact symbol/version/policy metadata, positive and negative cases, target compilation and idempotence evidence.
- [ ] Every R001-R039 topic is classified as detector, checklist, or both, with fixtures and a working guide anchor.
- [ ] Report-only execution preserves all input bytes; no search markers or hidden build-file edits occur.
- [ ] Unsupported patterns and incomplete analysis produce visible findings with correct module/source scope.
- [ ] All 14 email and 16 Mailer starter overloads have individual fixture coverage; shared implementation code is not a substitute.
- [ ] Java/Maven end-to-end examples run against exact candidate artifacts on the declared runner matrix; target compilation/runtime checks meet the stated Java baselines.
- [ ] Source-version claims match evidence; no rule is based on an unreleased intermediate API.
- [ ] Factory, send, future, shutdown and security boundaries match the published descriptions; no default policy is invented.
- [ ] The report companion rejects incomplete exports, generates deterministic usable reports, and implements the requested finding gate independently of patch existence.
- [ ] Fresh dependency resolution and artifact/license inspection confirm the documented installation route; recipe runtime dependencies do not include SJM implementation artifacts.
- [ ] Re-running the actual migration produces no further source/build changes and does not duplicate findings.
- [ ] Release notes distinguish automated edits, decisions, runtime checks and unsupported environments; no blanket behavioral-compatibility claim is made.

## Follow-up: Broader coverage

This phase expands how much can be migrated within the proven Java/Maven environment. It does not relax the evidence
or fixture requirements. Prioritize patterns seen in real, reviewed consumer runs and record each extension in the
same manifest before adding it to the default composite.

| Increment | Concrete work | Admission gate |
| --- | --- | --- |
| B1: expression and construction coverage | Dynamic DSN parser-based conversion; safe factory method-reference forms; bounded `new Email(builder)` replacement. | Preserve parser aliases/null/invalid behavior, evaluation and initialization timing, constructor/custom-builder semantics. Add adversarial controls as well as ordinary examples. |
| B2: execution/result usage | Completion-only future adapters, receipt consumers, `join`/`get` forms, and local no-flag mode inference from a complete non-escaping construction chain. | Track every use; preserve declared contracts or require an explicit API change. Checked catches, cancellation, completion mutation, public wrappers and custom implementations must not disappear. Remove builder `.async()` only when all dependent uses are covered. |
| B3: bounded configuration and Spring patterns | Convert a simple one-time loader/bootstrap plus all known consumers to an explicit snapshot/factory; migrate selected Spring injection patterns with chosen ownership. | Fixtures prove source inclusion/order, typed reads, missing sources, converter consistency, reload boundaries and fresh-versus-shared builder behavior. Partial data flow remains report-only. |
| B4: templates and lifecycle | Migrate narrowly specified DKIM defaults without discarding property templates; offer final-shutdown rewrites when that intent is explicit; consider direct Angus/JPMS dependency additions with complete evidence. | Preserve unrelated defaults/overrides, invalid-key timing, test-inbox routes, executor ownership and callback safety. No heuristic security fallback or inferred final shutdown. |
| B5: review tracking | Persistent acknowledgments keyed by stable fingerprints, with reason, owner and target/tool version; reconcile baseline/follow-up reports; add optional HTML rendering and CI policy. | Acknowledgments become stale when relevant code/target/policy changes. Missing syntax cannot auto-close runtime checks. Fixtures cover moves, duplicated sites, suppressions and unresolved findings across runs. |

Completion means that each admitted pattern has a published scope and passes old-input, transformed-target,
behavioral, unchanged-negative, and idempotence checks. It does not mean every review finding can be eliminated.
Keep whole-program DI redesign, unknown reflective behavior, real server capabilities and application security
decisions as explicit review responsibilities.

## Follow-up: Wider support

This phase expands supported environments after the Java/Maven contract is stable. Each environment gets its own
entry in the support matrix, runnable command, distribution proof and complete fixture project. Reuse semantic rules
where appropriate, but do not infer another language's support from Java attribution tests.
