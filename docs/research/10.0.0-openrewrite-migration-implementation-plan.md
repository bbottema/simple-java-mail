or validation fixtures are implemented by this document.

and the 52-topic accepted target migration inventory. This document owns scope, implementation order, and release acceptance.

- Email To/Cc/Bcc, Reply-To and notification conveniences parse every supplied mailbox, including group members. An

- Empty SMTP username/password strings normalize to absence in individual setters and all convenience overloads.

- The Spring executor example correction and first-use reordering add no recipe. R018/R035 retain executor ownership
  review: never insert shutdown or redesign beans automatically. Keep guide links/anchors synchronized with the reordered

### Repeated completion (R050)

[ADR 0037](../adr/0037-repeatable-email-completion.md) and [#768](https://github.com/bbottema/simple-java-mail/issues/768)
change ordinary template merging compared with released 9.x. Completion remains eligible for later selected-Mailer
defaults/overrides, but additive templates contribute only values not already present. Preserve supplied occurrences
and order, complete recipient metadata, suppression and unconditional applicable locks, including locked name completion.
Resource matching is conservative and performs no content I/O; unknown independent sources remain distinct.

Detect released completion/governance helpers and defaults/overrides configuration as evidence for R050. Also retain
a module-level runtime checklist when configuration or resource identity is not statically visible. Review whether an
application relied on templates to add repeated entries; never remove completion calls, deduplicate caller collections,
insert suppression/freeze flags or infer attachment sameness automatically. Header-key and whole-policy resolution,
local builder additions, exact EML and frozen retry behavior remain separate controls. Cover this in F24 and retain
related R024/R025/R027/R045 findings when their independent concerns apply. The migration anchor is
`repeated-email-completion`; compare the released runtime and final target instead of silently updating MIME goldens.

### Retry precedence and observer scope (target controls)

The retry correction in `549a48f0` / [ADR 0030](../adr/0030-safe-bounded-mail-send-retries.md) preserves unset policy
choices until the owning Mailer resolves explicit values, captured properties and built-in fallbacks. Locks remain
binding. Explicit resets/clears/disabling and default-valued explicit inputs remain distinguishable from omission.
Validate complete schedules and resource relationships after resolution; Java and properties can supply different
required fields. Supplied numeric getters retain absence, while OperationalConfig and the root Mailer builder's
policy getter expose resolved settings. `toBuilder()` preserves the source value's supplied/resolved choices and clears.

MailSendRetryPolicy is absent from the inspected released 9.0.0, 9.1.0 and 9.3.6 APIs. Extend F23 with these target
contracts, partial Java/property schedules, memory/message-size relationships, source isolation, locks, serialization,
CLI and Spring controls. Do not invent a released-source migration rule, nullable-getter rewrite or recipe that replaces
application policy construction to compensate for an unreleased defect.

[ADR 0012](../adr/0012-terminal-send-observation.md) retains the handler factory and existing transport-activating
signatures. Issue 3 from this review approves no handler/context overload or send-request API. Keep application-owned
correlation and callback lifetimes in target examples; never emit such nonexistent methods or invent a migration topic.

### Attachment resource construction (R051)

[ADR 0031](../adr/0031-public-api-and-internal-construction.md#attachment-resource-construction) replaces positional
AttachmentResource construction and optional-metadata Email overloads with a core resource builder. Keep the short
Path, byte-array/MIME and DataSource conveniences and their required-input pre-encoded equivalents. Singular resource
addition and named builder inputs are additive target capabilities; released Path convenience absence is not a removal.

Inventory the four AttachmentResource constructors, both `ofPreEncodedData` factories and ten optional-metadata
Email attachment/image overloads against each supported release. They are present in inspected 9.0.0, 9.1.0 and 9.3.6
sources; intermediate releases still need their version-manifest entries. Preserve the normal-versus-pre-encoded input
distinction and every name/description/Content-ID/encoding argument. Match full declaring types and descriptors, never
arity or spelling alone: a short pre-encoded byte convenience still legitimately takes four required inputs.

R051 reports removed constructor/factory/invocation sites. B7 below admits bounded typed rewrites only after the final
resource builder is frozen and evaluation/ownership checks pass. Constructor/method references, subclasses, custom or
nullable receivers, effectful argument expressions and ambiguous control flow remain review-only until separately proven.
Do not insert DataSource reads, copy borrowed sources, wrap bytes in an application-owned mutable source, collapse resource
identity, remove optional metadata or change encoding to make the target compile. CLI syntax and serialized field formats
are not automatically rewritten. The implemented guide anchor is `attachment-resource-builder`; the new target remains
unreleased and must still pass the ordinary frozen-artifact gate.

The implemented named target is `AttachmentResource.builder()` / `toBuilder()`, with source choices
`withDataSource(DataSource)`, `withData(byte[], String)` and `withPath(Path)`. Metadata setters are `withName`,
`withDescription`, `withContentId`, `withContentTransferEncoding` and `withPreEncodedContentTransferEncoding`.
Add the resulting value with `withAttachment(AttachmentResource)` or `withEmbeddedImage(AttachmentResource)`.
Map the following released descriptors exactly (fully qualify types in the actual manifest):

| Released family removed in the target | Descriptors / named target mapping |
| --- | --- |
| AttachmentResource constructors | `(String, DataSource)` and the three extensions adding description, description plus normal encoding, and description plus normal encoding plus Content-ID. Use `withName`, `withDataSource` and the corresponding named metadata setters, then `build()`. |
| `AttachmentResource.ofPreEncodedData` | `(String, DataSource, String, ContentTransferEncoding)` and its extra Content-ID form. Use the pre-encoded setter, never the normal encoder setter. |
| `withAttachment` byte forms | `(String, byte[], String, String)` and its extra normal encoding form. Preserve the MIME type through `withData`; description and encoding become named choices. |
| `withAttachment` source forms | `(String, DataSource, String)` and the extensions adding normal encoding and Content-ID. Preserve borrowed source identity through `withDataSource`. |
| `withPreEncodedAttachment` | `(String, byte[], String, String, ContentTransferEncoding)`, `(String, DataSource, String, ContentTransferEncoding)` and the latter's extra Content-ID form. Preserve pre-encoded input. |
| Embedded-image Content-ID forms | `withEmbeddedImage(String, DataSource, String)` and `withPreEncodedEmbeddedImage(String, DataSource, ContentTransferEncoding, String)`. Use singular image addition with the corresponding named resource. |

F25 must compile every supported direct rewrite against actual target artifacts and exercise null/name fallback, all
metadata, bytes/Path/source ownership, byte copying, pre-encoded content and argument/failure order. Use already-evaluated
arguments for initial candidates; early setter validation or copying must not run ahead of effects that previously preceded
the constructor/method body. Preserve the receiver's single evaluation and null-failure behavior. Unsupported sites remain
unchanged and reported; short retained calls and unrelated same-named methods are negative controls.

### Client-validation Boolean naming (R040)

[ADR 0003](../adr/0003-immutable-configuration-snapshots.md#client-validation-reporting) selects
`ValidationConfig.Builder.withClientValidationWarningsOnly(boolean)`. True retains the existing run-checks/log-findings/continue behavior;
false retains rejection. There is no enum or change of address-validation policy. Unset inherits captured properties before built-in false;
explicit reset/disable choices and applicable locks retain their usual meaning. Final-size and other preparation failures are separate.

The released root `MailerGenericBuilder.disablingAllClientValidation(Boolean)` and its reset/inspection companions belong to existing
R040 grouping coverage. Map the choice to the named Boolean on `ValidationConfig`, retaining the supplied group's unrelated values.
Source Boolean and target boolean differ for nullable/dynamic expressions: do not introduce earlier unboxing or failure timing without a
proven safe source. Preserve explicit false as a supplied choice, never mistake it for absence, and preserve reset versus inheritance.
The renamed ValidationConfig methods themselves were never released in 9.x; do not generate a separate unreleased-to-target recipe.
The released root `resetDisableAllClientValidations()` moves to `ValidationConfig.Builder.resetClientValidationWarningsOnly()`;

Inspection has two different migrations. Released `OperationalConfig.isDisableAllClientValidation()` maps directly to
`OperationalConfig.isClientValidationWarningsOnly()` with the same resolved primitive value. Released
`MailerGenericBuilder.isDisableAllClientValidation()` also returned a resolved primitive, but the target
`getValidationConfig().getClientValidationWarningsOnly()` exposes nullable supplied intent. Do not rewrite it to that
getter chain automatically or construct a Mailer merely to inspect a value. Keep that root-getter use report-only unless
equivalent effective-value access through an already available owner is proven. Verify these signatures for each source version.

Extend F19/B6 controls with true/false/absent choices, captured-property precedence, locks, explicit reset, nullable source arguments and
retained group members. Existing `simplejavamail.disable.all.clientvalidation`, typed raw-property identities and CLI option spellings/polarity

## First useful release

### Accepted typed configuration target (R009/R011)

Ordinary target reads use opaque invariant `ConfigKey<T>` values from `ConfigKeys`: `config.get(ConfigKeys.SMTP_PORT)`
returns nullable Integer; `config.get(ConfigKeys.SESSION_TIMEOUT)` returns nullable Duration. Both `valueOrProperty`
overloads constrain explicit and fallback values to that same T. Presence/source inspection accept the same key.
The catalogue binds parsers and Java projections together; no caller-class parameter or inferred-T legacy getter remains.
`Property` and `asMap()` retain explicit heterogeneous parser integration, including Integer milliseconds. All textual
keys/units, raw-source/lock representation, missing aggregate nulls, isolation, provenance and redaction stay intact.

Treat released static `ConfigLoader` calls separately from abandoned unreleased snapshot getters. In tag 9.3.6 the
named scalar getters and `valueOrPropertyAs*` methods perform conversions; `getStringProperty(SMTP_PORT)` legitimately
returns decimal text. A typed Integer read alone would change that contract. Literal matching-type reads are bounded
follow-up candidates only after snapshot ownership, valid-source/schema assumptions, null and evaluation behavior are
proven. Cross-type conversions, generic/dynamic Property values, fallback conversion, Duration/numeric consumers,
method references and application reload/DI policy remain conditional/report-only. Preserve the intended conversion
explicitly where a reviewed example needs it; never infer authentication/type intent from variable names or a port.

Extend F06 with Integer-to-String/null, duration/raw-unit/range, wrong-key compilation, invariant fallback and wildcard
map fixtures. Keep R001-R047 and T001-T008 unchanged; no typed-key recipe is implemented or added to the first composite
by this supplement. The existing released ConfigLoader/type migration topics link the
[normal typed-read guide](../../simplejavamail.org/src/pages/configuration.hbs#section-typed-config-keys).

Deliver a Java/Maven migration tool that can remove common 9.x compilation blockers, show a reviewable patch, and
produce a source-preserving report of application decisions and runtime checks. An application with unusual
configuration or lifecycle requirements must still receive useful findings when no source rewrite is appropriate.

The first release has three deliverables:

1. **Recipe library:** proposed artifact `org.simplejavamail:rewrite-simple-java-mail`, independently versioned from SJM,
   with public composites `org.simplejavamail.rewrite.MigrateToSjm10` and
   `org.simplejavamail.rewrite.ReviewSjm10Migration`.
2. **Report companion:** proposed executable artifact `org.simplejavamail:sjm-migration-report`, released at the same
   tooling version. It reads exported tables and writes `migration-report.md` and `migration-report.json`.
3. **Validation corpus:** real released-input projects, expected transformed projects, report expectations, and
   behavioral controls. These are development/CI assets, not application runtime dependencies.

Coordinates and names above are proposals, not published artifacts or commands users can run today. A separate
`rewrite-simple-java-mail` repository is the recommended eventual home. This plan does not create that repository.
Publish the first supported tooling release against a fixed SJM 10.0.0 release candidate or final artifact; label
candidate-only compatibility explicitly and revalidate before advertising final 10.0.0 support.

The accepted target retains OpenPGP signing/encryption configuration in serialized Email snapshots without changing
Email's format version or serial identity. Signing data includes secret key rings/passphrases; encryption-only data holds
public keys and cipher choice. Neither config type, module nor Email field exists in released `9.3.6`, so this target-only
correction is not a migration-guide topic, a new R rule or an automatic persistence-policy change. Keep R001-R047 and
T001-T008 intact. Frozen-target validation must retain configured protection/algorithms and exact protected bytes, read
supported older Email streams with omitted configuration absent, and check defensive graph restoration. Documentation
belongs in the normal serialization/security reference, not a rewrite of an application's key-storage policy.

### User workflow

1. Build/test the application on its existing 9.x dependencies. Resolve its real source version and active Maven
   modules/profiles. Record a source-control baseline and the tool/target versions.
2. Run `ReviewSjm10Migration` on the old classpath with data-table export enabled. Render the report, including analysis
   gaps and project-level runtime checks. A missing classpath or failed parser is an actionable result.
3. Choose factory and execution-mode policy for an explicit module/source scope. Without a choice, affected sites
   remain unchanged and carry a decision finding; unambiguous type/literal rules can still run.
4. Dry-run `MigrateToSjm10`, producing a patch and report. Parse the input using the old dependencies. Plan source
   changes before dependency edits; do not upgrade dependencies and then try to parse removed APIs from scratch.
5. Apply the same configured recipe set, inspect the patch, then compile/test against the target dependencies.
   Application owners complete the report's decisions and runtime checks. The tool does not auto-approve them.
6. Re-run to establish idempotence and detect remaining statically visible old API use. Keep the baseline report:
   disappearing old syntax must not erase a pending runtime or lifecycle review.

The published README must contain copyable, pinned Maven commands for report, dry run, apply, and companion rendering,
including a Windows/PowerShell form with quoted `-Dkey=value` arguments. Integration tests must execute those exact
examples. The report-only command must not require enabling the mutating composite.

### Common failures and explicit submission predicates (R037)

The final target removes `MailSubmissionReceipt.isAcceptedByServer()` and exposes
`isAcceptedForAtLeastOneRecipient()` plus `isFullyAcceptedForSubmission()`. Do not treat this as a safe naming rewrite from released 9.x:
the inspected 9.3.6 method returned whether its captured SMTP response was a positive completion reply. The intermediate unreleased 10.x
method already used any-recipient status, but intermediate prototypes are not recipe inputs. A released call requires an R037 finding for
the caller's intended question: any recipient accepted, every recipient accepted, or a positive response observed. The latter can be expressed
on the frozen target as `receipt.getSmtpResponse().map(SmtpServerResponse::isPositiveCompletionReply).orElse(false)`.
Even that candidate requires exact source-version semantics, normal attribution, a proven supported receipt receiver and evaluation/null behavior
fixtures; custom implementations, overrides and method references remain report-only until separately proven. Any-to-full is a semantic change.

The common root remains `org.simplejavamail.MailException`; its kind/optional-receipt getters are new ordinary capabilities rather than another
migration obligation. Released `EmailTooBigException` and `BatchTransportException` now join that root, and size failures can reach the caller
directly instead of as an outer wrapper's cause. SJM execution-admission rejection now uses `MailSendRejectedException`, including a borrowed
executor's rejection as its cause. Detect catch ordering, related alternatives in multi-catches, broad-versus-specific branches, thrown/constructor
types, cause-chain assumptions and future unwrapping. These are conditional/report-only under R037: changing the catch type alone can make a
branch unreachable, capture unrelated application failures or change handling. Preserve provider causes, exact observer/completion identity,
partial/unknown acceptance and cleanup-after-acceptance. A kind never establishes retry safety.

Released 9.3.6 single-send and simple-batch wrappers also hid RuntimeExceptions from CustomMailer/iteration behind `MailException`.
The final target preserves those original application exceptions. Report broad catches that may have doubled as application-error handlers;
do not widen a library catch to RuntimeException automatically or infer which business failures should be recovered.

Keep T001-T008 unchanged. No production exception recipe or blanket predicate rename is authorized here. Documentation-only decisions about
additive copying, handler correlation, clear/reset scopes and completion-only streaming batches add no released migration topic or recipe.
Only actual released behavior or removed released signatures belong in the migration inventory and guide.

### Accepted target grouping and the first-release boundary

The [research supplement](10.0.0-openrewrite-migration-research.md#current-target-supplement-accepted-configuration-groups)
maps released scalar and positional-crypto signatures to the accepted seven Mailer groups, four Email groups and
direct typed crypto calls. A name-based enum conversion or factory rewrite is no longer sufficient for callers whose
remaining root setting methods moved. Target fixtures must compile the complete generated expression, with every
unsupported residual site clearly reported.

Keep T001-T008 as the eight first-release responsibilities. Broad scalar-to-group consolidation and positional crypto
rewrites are initially report-only under R040/R041; B6 below is their conditional follow-up. T003's narrow typed
options edit is the necessary complete target form of that existing DSN-literal responsibility, not a ninth rule.
It must remain unchanged/report-only when its bounded local-receiver proof fails.
T004 must likewise express the three released static debug starters through a fresh `SessionDebugConfig`, rather
than retain a removed flat debug setter. Preserve independent activation, output/printer identity and null behavior;
its existing factory/evaluation preconditions still apply. This is complete starter migration within T004.

Do not wrap separate assignments in fresh groups. Replacing a group drops earlier supplied members; editing through
its `toBuilder()` retains them, while `useConfigured...Config()` restores captured inheritance. These operations
cannot substitute for each other or for field-specific clear/reset/disable choices. Preserve Email copy/default/
override behavior, mandatory locks, supplied Session settings and caller-owned executor/factory lifetimes.
Retain explicit empty Java strings and their field-specific validation/clearing behavior; blank property-source entries
being absent does not make an explicit setter argument equivalent to omitting that group member.
Use the normal guide's [operation table](https://www.simplejavamail.org/configuration.html#configuration-operations) and
[scope/precedence table](https://www.simplejavamail.org/configuration.html#configuration-precedence) when reviewing those controls.
They explain unchanged policy semantics; the documentation pass adds no migration topic or recipe and does not expand R001-R047 or T001-T008.

For example, a future pool-only candidate may combine a contiguous setter run on a fresh non-escaping builder with
effect-free local/literal arguments. An edit on a previously configured builder must preserve its supplied group
through `getConnectionPoolConfig().toBuilder()`. Aliasing, branches, interleaved groups/getters, method references,
custom builders, dynamic/null receiver expressions or uncertain prior state block an automatic rewrite.

The released crypto source signatures are `signWithDomainKey(byte[], String, String, Set<String>)`,
`signWithSmime(File, String, String, String, String)` and `encryptWithSmime(File, String, String)`.
Their typed targets preserve exclusions, passwords/alias, null algorithms, byte copying and immediate file parsing/
closing. Inline construction can move IO or copying before later effectful argument evaluation; future patterns must
prove unchanged evaluation/failure order or report. Null DKIM exclusions must omit the setter on a fresh config
builder or retain the Set type; emitting a bare null would be ambiguous against its Set/varargs overloads.
Do not treat the two removed unreleased `Path` shortcuts, the
unreleased Java queue-overflow setters, or unreleased rate-limit scalars as 9.x inputs.

Property keys, Spring metadata and scalar CLI option syntax keep their contracts; no text rewrite is authorized by
Java grouping. Keep the receipt source-version distinction and mailbox/Reply-To decisions separate.
Repeated `withReplyTo` calls remain additive; this plan must not invent semantic replacement APIs or migration warnings.

### Accepted Email address-list behavior and notification reads

R047 reports source-version-specific interpretation changes: released 9.3.6 String Reply-To/notification calls could
select the first parsed mailbox; the target parses them all. From/bounce remain singular and reject recognized lists
and groups. Name fallback, malformed input and InternetAddress representation need separate released-input/frozen-target
controls. T004 must retain the related review finding after a bootstrap rewrite; do not insert clearing calls, select a
mailbox, change individual Recipient extraction, or infer display-name intent. Repeated Reply-To remains additive.

R048 covers released Email/EmailPopulatingBuilder `getDispositionNotificationTo()` and `getReturnReceiptTo()` reads.
Their target plural getters return `List<Recipient>`, not nullable Recipient. Detect scalar consumers, null tests, method
references, public signatures and notification requests with omitted destinations or multiple Reply-To values. Preserve
request flags independently from list emptiness. Default to source-preserving review: no blanket rename, automatic
`.get(0)`, null-to-emptiness rewrite, singleton assumption, or first-Reply-To compatibility restriction is authorized.
The read methods exist in inspected 9.0.0, 9.1.0 and 9.3.6; require exact manifests for other claimed versions.

R049 covers potentially empty credentials on released individual username/password setters and the three-argument SMTP
overload. Confirmed behavioral evidence is 9.3.6; inspect intermediate versions before extending that source envelope.
Keep four-argument normalization, null/nonempty/whitespace values, retained password and token-provider choices as controls.
Report literal emptiness or unresolved dynamic input without exporting credential contents. Do not normalize input,
swap overloads, choose authentication policy or modify configuration/CLI text automatically.

These are reporting/fixture obligations. Keep T001-T008 unchanged and distinguish notification requests from SMTP
submission receipts and their separate R037 predicates.

The exact-Email copying clarification is documentation only: the existing target behavior remains editable composition,
without byte identity or guaranteed validity of already applied signatures. It neither strips nor re-signs signatures
automatically. R039's human byte-intent review may point to reusing the original exact Email or rebuilding its explicit
envelope from authoritative finalized input. Do not invent an exact-copy API, released-9.x semantic migration, or an
automatic preservation/re-signing recipe for this clarification.

### Explicit first-release exclusions

- `shutdownConnectionPool()` renaming and adding/blocking close: report final-shutdown and drain ownership.
- Future-to-`MailSend` wrappers, cancellation adapters, public return-type changes, and no-flag mode inference.
- Removing builder `.async()` while dependent operations still need a decision.
- Rebuilding static configuration as DI/application factories, global reloads, or Spring bean redesign.
- DKIM default/override template conversion, security fallback changes, and automatic suppression of SMTP checks.
- Broad advanced scalar/companion consolidation and positional DKIM/S/MIME rewrites; collect R040/R041 evidence.
  T003 has only its explicitly bounded DSN-literal/options edit, with unsupported sites unchanged.
- Direct `Email` construction, result/exception construction, custom implementation migration, and serialization repair.
- Adding Angus/JPMS dependencies from incomplete evidence or changing provider-specific delivery code.
- Updating raw MIME goldens, clearing recipient overrides, or normalizing invalid configuration just to make tests pass.

Every exclusion must yield a concrete source finding when detectable, or an explicitly scoped checklist item where
the evidence is external. An exclusion is not permission to silently ignore the topic.

## Implementation structure and ownership

Use one independently versioned repository with the following responsibilities; exact directory names can follow
the OpenRewrite recipe-library template when implementation begins.

| Component | Owns | Must not own |
| --- | --- | --- |
| `recipe` artifact | Public composites, typed Java visitors, Maven changes, options and preconditions. | Application runtime configuration, network SMTP activity, or report presentation. |
| `analysis` package within the recipe artifact | Per-run scan accumulator, symbol/version resolution, bounded local ownership facts, coverage accounting. | Global mutable caches, cross-run application state, or whole-program certainty claims. |
| Versioned rule manifest resource | Stable T/R IDs; old/target signatures; supported versions; policy; guide anchors; detector/checklist classification; fixture references. | A second copy of migration prose that drifts from the guide. |
| Report tables in the recipe artifact | Schema-versioned findings, run metadata and analysis-coverage rows. | Source markers or edits in report-only mode. |
| `report-cli` artifact | Read one explicit run's tables, normalize paths/statuses, render JSON/Markdown, apply requested exit policy. | Re-running Maven, resolving application classes, or changing source/build files. |
| `validation-fixtures` and CI harness | Isolated input/output builds, semantic controls, snapshots, tool-distribution checks and release gate. | Publishing application dependencies or editing the SJM checkout under test. |

Use built-in `ChangeType`/`ChangeMethodName` behind appropriate preconditions where they fit. Use custom visitors for
DSN arguments, factory chains, mode calls and report-only scanning. Use a scanning recipe where ownership facts must
be gathered before a rewrite. Restrict all accumulator state to a run and module; fixture parallelism must not leak policy.

Keep old and target symbols available for recipe authoring without putting two incompatible SJM versions on the
consumer application classpath. Generate/use versioned type tables or parser resources for attribution and JavaTemplate
construction; target API classes are not production runtime dependencies of the recipe artifact. Follow OpenRewrite's
[multiple-version guidance](https://docs.openrewrite.org/authoring-recipes/multiple-versions) and
[recipe test guidance](https://docs.openrewrite.org/authoring-recipes/recipe-testing).
Do not disable type validation to hide a failing generated tree.

Use JDK 21 to author/build the tooling while compiling its production bytecode for the declared JDK 17 runner floor.
Test the packaged recipe and companion on JDK 17, not just the authoring JVM, to catch accidental linkage to newer APIs.

The composite must collect baseline findings before mutating source/build declarations. Verify the ordering with the
pinned runtime: subsequent cycles, generated target types, and Maven model refresh must not lose old-symbol matches
or generate duplicate findings. A fresh application compilation is a separate process against target dependencies.

## Report companion specification

### Tables and schema

Provide three custom data tables, exported using stock OpenRewrite facilities:

| Table | Required fields |
| --- | --- |
| `SjmMigrationRun` | Schema/tool versions, run ID, review/dry-run/apply mode, source version per module, target version/hash, plugin/core/JDK versions, active modules/profiles and sanitized policy selections. |
| `SjmMigrationFindings` | Stable rule ID, topic ID, module, normalized repository-relative path or module scope, line/column when available, enclosing symbol, evidence kind, status, concise reason, required action, guide URL, stable fingerprint. |
| `SjmMigrationCoverage` | Module/language/source-set and recognized resource scope, candidate/analyzed/excluded/unparsed counts, attribution failures, unsupported-version/language/build reasons, and each topic's detector versus checklist coverage. |

Include enough run metadata to detect missing tables and incompatible schemas. No table rows may contain passwords,
tokens, raw configuration values, arbitrary Java argument literals, full source lines, or machine-specific absolute
paths. Use symbols and redacted evidence labels. Format CSV correctly for commas, quotes and newlines, and prevent
spreadsheet-formula interpretation of attacker-controlled text fields in exported views.

Status vocabulary:

- `change-proposed`: dry-run patch contains this supported transformation.
- `change-applied`: apply execution recorded this transformation; target compilation remains a separate check.
- `decision-needed`: source/build evidence requires an application choice or unsupported edit.
- `runtime-review`: a behavior must be validated against application data, environment, or lifecycle.
- `unanalysed`: the requested scope could not be assessed reliably.

Use confidence/evidence kinds such as `typed-match`, `literal-config`, `bounded-flow`, and `project-checklist`.
A project checklist must not pretend to be a line-specific defect. Record an unavailable position explicitly rather
than assigning a misleading line. Keep column/line acquisition independent of formatting changes.

Fingerprints combine stable rule/topic ID, module, normalized path, enclosing symbol and normalized occurrence
context; exclude line number, timestamps and secret values. Deduplicate across cycles without collapsing distinct
call sites. Preserve all reasons when several topics apply to one site. Establish this behavior with fixtures before
introducing a persistent acknowledgment ledger.

### Human-facing output

The Markdown report starts with the tool/target/source versions and a coverage summary. It then lists:

1. Unanalysed scope and decisions blocking compilation or policy selection.
2. Proposed/applied source changes with links to the diff and source locations.
3. Behavioral/runtime checks grouped by migration topic with direct guide links.
4. Unsupported/excluded scope and the exact commands/versions used to produce the report.

Each finding must answer: what was found, why it matters, what the owner should do, and where the explanation lives.
The first release needs Markdown and JSON only; HTML is a later renderer. Include the report in generated build
output (`target/sjm-migration/<run-id>/`), not among the application's tracked sources by default.

The companion takes an explicit table/run directory and output directory. It must not guess the newest timestamped
directory and accidentally combine separate runs or modules. Integration tests will establish how Maven reactor
outputs are aggregated and associated with one run.

Use these exit-code semantics:

| Exit code | Meaning |
| --- | --- |
| 0 | Valid report produced; this alone does not mean the migration is complete. |
| 1 | Invalid/missing input, unsupported schema, inconsistent run metadata, or report-generation failure. |
| 2 | An explicitly requested finding gate matched unresolved statuses. |

The optional gate accepts a list of statuses, for example `decision-needed,unanalysed`; a user may include
`runtime-review` if every runtime checklist must be closed elsewhere before CI passes. Do not reuse Maven's
`failOnDryRunResults` as a finding gate: table-only findings can exist without a diff.

### Review-only guarantees

`ReviewSjm10Migration` returns the original source/build trees and exports tables only. Hash all input source,
resource and build files before and after the integration test. Build-directory output is allowed; tracked file
changes and `SearchResult` markers are not. Validate parser/error cases as well as successful matches.

Keep baseline and follow-up reports separate and reference the baseline from the follow-up. A finding may disappear
because its old API was changed; that does not automatically resolve a runtime review. The first release leaves
acknowledgments with the application owner. A machine-managed ledger and cross-run reconciliation belong to Broader coverage.

## Validation fixtures

### Corpus layout and execution

Store each case with an ID, source SJM version, target artifact identity, policy, input sources/build files, expected
patch or unchanged files, expected findings/coverage, and the assertion being tested. Keep source snippets small
enough to explain a rule. Also keep complete Maven projects to catch classpath, packaging and reactor errors that
snippet tests miss.

For every transforming rule, run these distinct checks:

1. Compile the untouched input against the real supported 9.x artifact in an isolated workspace/cache.
2. Run RewriteTest before/after and negative cases with type validation enabled; assert a subsequent recipe cycle
   makes no additional change.
3. Execute the published Maven invocation on the input project, inspect patch/report expectations, and apply.
4. Compile the actual transformed project against the frozen target artifact in a separate process. Resolve target
   artifacts by the recorded identity, not by whatever is installed in the developer's Maven repository.
5. Run a second full invocation and assert an empty source/build diff, no duplicated report rows, and accurate scope.
6. Run the relevant behavioral assertion when the transformation touches evaluation, configuration or execution.

Expected output compilation is not sufficient: the harness must compile the output actually produced by the recipe.
Keep released-input and target-output classpaths separate. API-only scans of other 9.x releases supplement these
fixtures; they do not substitute for the representative end-to-end builds.

Successful target compilation is required for fixtures that claim a complete supported migration. Negative fixtures
must compile as released input, remain unchanged at the unsupported site, and emit the specified finding; they may
still fail against 10.0.0 until an application decision is applied. Mixed supported/unsupported fixtures must label
that partial result explicitly. Do not make a test pass by deleting the unsupported site or claiming its target build
succeeded. Already-invalid input belongs to the incomplete-analysis corpus with the original failure recorded.
