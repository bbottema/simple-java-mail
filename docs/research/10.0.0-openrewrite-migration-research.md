# SJM 9.x to 10.0.0: OpenRewrite migration research

Research date: 2026-10-19. Status: investigation complete; production recipes and report companion are not implemented.
The [implementation plan](10.0.0-openrewrite-migration-implementation-plan.md) defines the proposed first release and subsequent phases.

## Recommendation

Publish an independently versioned, Apache-licensed OpenRewrite recipe library, provisionally
`org.simplejavamail:rewrite-simple-java-mail`, together with a small migration-report companion.
Use it to remove repetitive, type-attributed Java migration work and give the remaining decisions a precise location,
explanation, and migration-guide link. Do not describe it as an unattended behavioral upgrade.

The first useful release should concentrate on builder entry points, explicit send modes within a narrow supported
envelope, simple type/method changes, literal DSN options, dependency alignment, and an actionable report.
Configuration ownership, lifecycle, delivery policy, and runtime compatibility need explicit application decisions.
They still belong in the report even when the recipe cannot change the source.

OpenRewrite explicitly recommends that library maintainers ship recipes for breaking changes in a separate library.
Its declarative recipes, typed Java visitors, scanning recipes, tests, and data tables fit this split.
See [automating breaking changes](https://docs.openrewrite.org/authoring-recipes/automate-breaking-changes),
[recipe types](https://docs.openrewrite.org/authoring-recipes/types-of-recipes), and
[recipe concepts](https://docs.openrewrite.org/concepts-and-explanations/recipes).

The [local migration guide](../../simplejavamail.org/src/pages/migration-notes-10.0.0.hbs) is the topic inventory.
The [website's migration scope policy](../../simplejavamail.org/content-plan/migration-support.md) requires comparison
with released behavior. Recipes must not migrate between abandoned, unreleased 10.x prototypes.
For example, `MailTransportAdapter` and `MailTransportResult` were not APIs in 9.3.6.

Submission receipts also require a source-version distinction. `MailSender` and `withOpenConnection` existed in 9.0.0;
receipt APIs arrived in 9.1.0, following commit `ed49cccd` (`feat(smtp): expose submission receipts`).
A rule for a receipt method is not applicable to every 9.x version merely because the method exists in 9.3.6.

An early guide/source mismatch around the `Email` constructor was observed during research. On saving this document,
the current [Email source](../../modules/core-module/src/main/java/org/simplejavamail/api/email/Email.java) declares
the builder constructor `protected` and `@ApiStatus.Internal`, matching the migration guide. This is no longer an
unresolved mismatch, but it demonstrates why recipe tests must use a frozen target artifact.

The current [SimpleJavaMail factory](../../modules/simple-java-mail/src/main/java/org/simplejavamail/api/SimpleJavaMail.java)
returns a shared, lazily initialized conventional configuration snapshot from `fromDefaults()`.
Repeated calls do not create fresh snapshots. `withConfig(...)` creates an independent factory.
This makes conventional factory insertion practical, but does not preserve applications that mutate or reload the
old global configuration after initialization.

## What can be automated

The classifications below describe feasibility, not implemented guarantees:

- **Automatic:** a typed change with a narrow, mechanically verifiable contract.
- **Conditional:** requires a checked source pattern or an explicit application policy.
- **Report:** identify evidence and explain the decision; do not change the source by default.
- **Runtime review:** source inspection can supply hints, but cannot establish compatibility.

### Types, methods, builders, and enum arguments

| Change | Assessment | Implementation shape and limits |
| --- | --- | --- |
| `internal.config.EmailProperty` to `api.email.EmailProperty` | Automatic | Built-in `ChangeType`, including static imports. Match the exact SJM type, not a spelling. Preserve enum choices and template suppression intent. |
| Scoped `MailSender.sendMailAndGetReceipt(email)` to `sendMail(email)` | Automatic in library-owned scopes | Both return a direct `MailSubmissionReceipt`. Use an exact method matcher and restrict ownership; do not rename application declarations or custom implementations. This is different from the old top-level `Mailer` future API. |
| Valid constant DSN strings to enum arguments | Automatic within validated literals | Custom typed visitor or Refaster template. For example, `"FAILURE,DELAY"` becomes `NotifyOption.FAILURE, NotifyOption.DELAY`, and `"HDRS"` becomes `ReturnOption.HEADERS_ONLY`. Preserve aliases and order. Invalid, empty, null, or ambiguous arguments must not silently acquire different behavior. |
| Dynamic DSN strings | Conditional; follow-up | The removed String overloads delegated to `parseReturnOption` and `parseNotifyOptions`, which remain available. A parser expression, including conversion to `NotifyOption[]`, is feasible. Preserve single evaluation, invalid/null behavior, and exception order, including a null receiver. |
| All `EmailBuilder` starters | Conditional on factory policy | The guide inventories 14 overloads: starting blank; copying `Email`, builder, or MIME; reply/reply-all variants; forwarding `Email` or MIME. Replace the declaring factory, preserving overloads and arguments. |
| All `MailerBuilder` starters | Conditional on factory policy | The guide inventories 16 overloads: session, build, transport, OAuth, three SMTP-server overloads, individual SMTP fields, debug options, custom Mailer, and logging-only mode. `usingSession(s)` becomes `factory.mailerBuilder(s)`; other starters use the appropriate fresh builder. |
| Concrete builder variables | Conditional | Change local implementation-typed variables to public builder interfaces only when every use remains valid. Do not apply a global implementation-to-interface `ChangeType` to subclasses, fields, public contracts, or implementation-only calls. |
| Recipient builder construction | Conditional | Simple no-argument construction can move to `factory.recipientBuilder()` / `factory.recipientsBuilder()`, with `IRecipientBuilder` / `IRecipientsBuilder` declarations. Custom constructors, subclasses, and escaping implementation types require review. |
| `new Email(builder)` | Conditional; initially report | `builder.buildEmail()` is the intended public construction path. Check target visibility, custom builders, null behavior, result class, and validation before automating a bounded case. Serialization and subclass reconstruction are separate decisions. |

An application must choose its configuration source before factory rewrites. A conventional-defaults policy can insert
`SimpleJavaMail.fromDefaults()`; an existing-factory policy can use a proven accessible factory. Neither permits a
recipe to invent application DI wiring, tenant scope, or reload behavior. Method references also need care: replacing
a static reference with a bound reference can move factory initialization to reference creation.

The built-ins are documented at [ChangeType](https://docs.openrewrite.org/recipes/java/changetype) and
[ChangeMethodName](https://docs.openrewrite.org/recipes/java/changemethodname).
More involved changes need [typed Java templates](https://docs.openrewrite.org/concepts-and-explanations/javatemplate)
and explicit [type-attribution checks](https://docs.openrewrite.org/reference/type-attribution), not regular expressions.

### Send modes, futures, and shutdown

| Change | Assessment | Reason |
| --- | --- | --- |
| Literal boolean send mode with discarded result | Conditional | `sendMail(email, false)` can select `.sync()`, and `true` can select `.async()`. Cover batches separately. Verify library ownership, receiver/argument evaluation, and accepted exception-timing changes. |
| Literal boolean connection test | Conditional | Async testing still returns `CompletableFuture<Void>`; synchronous testing returns void. Result consumption determines whether a replacement is valid. |
| Omitted mode | Conditional or report | Released no-flag calls consult the Mailer's operational async setting; the builder default is false, and `.async()` changes it. An injected Mailer has no statically known mode. Require bounded construction evidence or an explicit scope policy. |
| Removing builder `.async()` | Conditional | Remove it only after accounting for all operations using that builder/Mailer. Do not erase the old policy while leaving dependent operations unresolved. The removed CLI `--mailer:async` setting needs a separate text finding. |
| Async receipt future to `MailSend.getCompletion()` | Conditional; follow-up | A completion future is only one facet of `MailSend`. Current `getCompletion()` is detached; cancellation of that future is not a request to cancel the send. |
| Old `CompletableFuture<Void>` wrappers | Report initially | A completion-only adapter such as `.getCompletion().thenApply(receipt -> (Void) null)` can retain a Java signature, but does not prove cancellation, completion mutation, ownership, or lifecycle equivalence. |
| `shutdownConnectionPool()` to `closeAsync()` | Report initially | A method rename is mechanically possible but changes lifecycle behavior. Final-shutdown intent must be established. |

The old [Mailer API](https://github.com/bbottema/simple-java-mail/blob/9.3.6/modules/core-module/src/main/java/org/simplejavamail/api/mailer/Mailer.java)
returns `CompletableFuture<Void>` from send methods and receipt futures from its receipt methods.
The current [Mailer API](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/Mailer.java) exposes
synchronous direct receipts and asynchronous [MailSend](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/MailSend.java)
handles. `requestCancellation()` is explicit. Public wrappers deserve review even if a return-type adapter compiles.

Inserting `.sync()` or `.async()` also changes where a null receiver fails relative to argument side effects.
The first release should reject unproven receivers or expressions instead of duplicating evaluation or assuming this
is irrelevant. Literal mode selection does not, by itself, establish exception or cancellation compatibility.

The released [shutdown implementation](https://github.com/bbottema/simple-java-mail/blob/9.3.6/modules/simple-java-mail/src/main/java/org/simplejavamail/mailer/internal/MailerImpl.java#L506)
shuts down an owned executor and cleans up pools, or returns a completed future where no pool cleanup is needed.
It does not establish the target's universal operation-admission and drain contract. The target
[Mailer implementation](../../modules/simple-java-mail/src/main/java/org/simplejavamail/mailer/internal/MailerImpl.java)
shuts down admission, drains operations, and then completes cleanup. Later use, externally supplied executors, and
shutdown inside callbacks all require examination; blindly introducing blocking close in a callback can deadlock.

Preparation timing differs within the source range too. In 9.0.0 async preparation could throw on the caller;
9.3.6 still prepares on the caller but catches runtime failures into a failed future; the 10.x async path prepares
during execution. Tests must identify their source version instead of asserting one universal 9.x behavior.

### Configuration, providers, and build files

| Change | Assessment | Required decision or evidence |
| --- | --- | --- |
| Static `ConfigLoader` loading and reads | Report; bounded follow-up possible | Preserve source inclusion and order, reload semantics, typed conversion, missing sources, map behavior, and every affected consumer. The old loading path appended environment/system settings; a new explicit snapshot must choose that policy. |
| Static conversion helpers and explicit factories | Report | Migrating a builder does not automatically make unrelated converter calls use the same explicit configuration. Track ownership across consumers. |
| DKIM Mailer defaults to email templates | Report; bounded follow-up possible | A new blank defaults template can discard other property-derived defaults. Copying a template and then clearing DKIM can read an invalid key before the clear, unlike an old bypass. Defaults and overrides are not interchangeable. |
| Spring default builder injection | Report | Replacing a shared mutable builder bean with a factory/fresh builders changes state sharing. Also inspect auto-discovery, context ownership, and property precedence. |
| Embedded-image route flags | Report | Old behavior and workarounds around the URL/classpath flags need application intent; swapping settings automatically can reverse a deliberate workaround. |
| Direct Angus dependency / JPMS `requires` | Conditional | Direct typed Angus imports can justify a compile dependency and module requirement. Respect dependency management, scope, versions, and provider choice. Reflection, generated code, and external consumers escape this scan. |
| SJM module version alignment | Automatic within known build declarations | Upgrade only a maintained allowlist of SJM application modules. Do not wildcard every artifact in the group, including the recipe artifact itself or unrelated libraries. |
| Java baseline | Explicit opt-in build change plus report | SJM libraries need Java 11; the CLI needs Java 17. Updating a compiler setting cannot upgrade the deployment JVM or prove compatibility of the rest of the application. |

## Report companion: what OpenRewrite provides

OpenRewrite already supports custom [data tables](https://docs.openrewrite.org/authoring-recipes/data-tables).
A review recipe can insert a finding row while returning the original syntax tree unchanged. No custom Maven plugin
is required for this. The normal console primarily reports recipe activity, changed files, and patch locations;
it does not replace a linked, prioritized migration report.

Built-in searches, such as [FindMethods](https://docs.openrewrite.org/recipes/java/search/findmethods), commonly add
`SearchResult` markers rendered as `/*~~>*/`. In the tested Maven plugin 6.46.1, `runNoFork` wrote those markers into
the actual Java file. A marker-based review recipe is therefore unsuitable as the default source-preserving report.
Do not generalize documentation for a newer version into a guarantee for the pinned runtime.

The proposed companion should consume the data tables and produce a readable Markdown summary plus a stable JSON
representation. It should include source locations, reasons, confidence/evidence type, required actions, and guide
links. A later HTML renderer can consume the same representation. The companion does not perform transformations.

The report must also expose incomplete analysis: unresolved types, failed parsers, exclusions, unsupported languages,
unknown versions and missing modules. A zero-finding result with incomplete coverage is not a clean migration.
Runtime checklist items must survive a source rewrite; removal of an old method name is not proof that its behavioral
review is complete. Stable fingerprints should use rule, relative path and symbol context, rather than line alone.
Avoid storing credentials, arbitrary argument literals, complete source excerpts, or absolute user paths.

Maven's `exportDatatables` exports CSV files. The experiment produced them beneath
`target/rewrite/datatables/<timestamp>/`, and a dry-run patch at `target/rewrite/rewrite.patch`.
Documentation and plugin versions can differ on default locations, so the supported runner must capture the actual
run directory explicitly. `failOnDryRunResults` detects source differences; it does not gate unresolved rows emitted
by a table-only recipe. A report CLI must supply any finding-based exit policy.
See the [Maven plugin reference](https://docs.openrewrite.org/reference/rewrite-maven-plugin) and
[Gradle plugin configuration](https://docs.openrewrite.org/reference/gradle-plugin-configuration).

## Distribution, licensing, and toolchain availability

The following observations are dated 2026-10-19 and must be refreshed when publishing. Distinguish artifact licenses,
repository access, and hosted-service subscriptions.

| Question | Finding |
| --- | --- |
| Can SJM publish its own Apache-licensed recipes? | Yes. The Apache-licensed OpenRewrite core/plugins and the Java facilities used here support a separately published recipe library. Check individual third-party recipe licenses rather than treating the entire ecosystem alike. |
| Is a hosted migration subscription required for this proposal? | No. The proposed recipes and report run locally. Hosted features or separately licensed recipes are independent choices. |
| What do current distribution docs say? | Recent releases, including Maven/Gradle plugin artifacts, are directed to authenticated `https://artifacts.codegenomeproject.org/maven`. Apache artifacts are described as free with authentication; other licensing/subscription terms apply to other artifact families. |
| What remains on Maven Central? | Metadata reported Maven plugin 6.46.1 and rewrite-core 8.90.4. Plugin 6.46.1 itself depends on core 8.89.0 and polyglot 2.11.1; this was the tested combination. The latest core metadata is not evidence for a tested plugin override. |
| Did the anonymous new-artifact probe work? | One anonymous request for the 6.50.0 plugin POM returned HTTP 200 with a real POM through a signed redirect, and referenced core 8.93.0. Central returned 404 for that version. This does not establish anonymous resolution of the complete toolchain or override the documented access policy. Do not retain expiring signed URLs. |
| What about Gradle? | Plugin Portal metadata exposed 7.41.0 and its plugin POM; the corresponding actual plugin artifact was not on Maven Central. This was metadata inspection, not a successful full Gradle execution or proof that every dependency resolves anonymously. |
| Which JDK/Maven requirements are proven? | The successful fixture used JDK 17 and Maven 3.9.10. The 6.46.1 plugin descriptor advertises Java 8/Maven 3.3.1, while current general docs recommend newer Maven; do not turn descriptor minima into an untested support promise. Current recipe-authoring guidance uses JDK 21. |

A first release can pin the demonstrated Central-only Maven runtime, or validate the newer distribution route and
document its setup. Building OpenRewrite from source is another possibility, with an additional maintenance burden.
Do not make a changing artifact repository or a hosted product account an unstated prerequisite.

## Alternatives and complementary tools

| Tool | Useful role | Limitation for this migration |
| --- | --- | --- |
| IntelliJ migration maps | Shareable package/class mappings for simple moves. | Do not express factory/configuration/lifecycle decisions or provide the required build-independent report workflow. |
| IntelliJ structural search/replace | Previewable shared templates and inspections for local source patterns, including several JVM languages. | Type/scope/build orchestration and a common migration report still need separate ownership. |
| Error Prone Refaster | Typed before/after expression templates; OpenRewrite also supports Refaster recipes. | Useful for narrow rules, not sufficient for cross-file configuration/lifecycle analysis. Current Error Prone requires JDK 21; older compatible versions need explicit pinning. |
| Spoon | Rich typed Java model and source transformation, including a source-preserving printer. | More parser, build integration, distribution, testing and reporting infrastructure would belong to SJM. |
| JavaParser and Symbol Solver | Java parsing, resolution and custom transformation. | Similar infrastructure cost; symbol resolution alone does not solve application intent. |
| japicmp / Revapi | Repeatable released-API differences and CI controls against forgotten public changes. | Complements the rule manifest; API diffs do not identify every behavioral migration or repair consumers. |
| Reviewed AI-assisted edits | Apply application-specific choices using the report and project tests. | A useful follow-up, not a deterministic recipe release contract. |

maintainer-owned library because its existing build integration and test/report facilities reduce infrastructure work.

## Decisions carried into the plan

1. Keep transformations separate from a source-preserving review recipe and report renderer.
2. Parse released source with its old classpath, then compile expected output separately against a frozen target.
3. Require explicit factory/mode policy where the application owns the choice; skip and explain unsupported cases.
4. Treat every guide topic as a coverage obligation, including runtime checks and unanalysed scope.
5. Ship deterministic Java/Maven support first, with a specific fixture and publication gate for every claimed capability.
6. Expand automation in **Broader coverage**, then expand supported environments in **Wider support** as defined in the
   [implementation plan](10.0.0-openrewrite-migration-implementation-plan.md).
