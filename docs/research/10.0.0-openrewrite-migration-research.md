  Automatic requests use all resolved Reply-To addresses, falling back to From. Notification destinations never become

  replace application policy construction or infer intended defaults.
- The Spring executor example correction and first-use reordering add no recipe. R018/R035 retain executor ownership

## What can be automated

The classifications below describe feasibility, not implemented guarantees:

- **Automatic:** a typed change with a narrow, mechanically verifiable contract.
- **Conditional:** requires a checked source pattern or an explicit application policy.
- **Report:** identify evidence and explain the decision; do not change the source by default.
- **Runtime review:** source inspection can supply hints, but cannot establish compatibility.

### Types, methods, builders, and enum arguments

| --- | --- | --- |

An application must choose its configuration source before factory rewrites. A conventional-defaults policy can insert

recipe to invent application DI wiring, tenant scope, or reload behavior. Method references also need care: replacing
a static reference with a bound reference can move factory initialization to reference creation.

The built-ins are documented at [ChangeType](https://docs.openrewrite.org/recipes/java/changetype) and

and explicit [type-attribution checks](https://docs.openrewrite.org/reference/type-attribution), not regular expressions.

### Send modes, futures, and shutdown

| Change | Assessment | Reason |
| --- | --- | --- |
| Literal boolean send mode with discarded result | Conditional | `sendMail(email, false)` can select `.sync()`, and `true` can select `.async()`. Cover batches separately. Verify library ownership, receiver/argument evaluation, and accepted exception-timing changes. |
| Literal boolean connection test | Conditional | Async testing still returns `CompletableFuture<Void>`; synchronous testing returns void. Result consumption determines whether a replacement is valid. |
| Omitted mode | Conditional or report | Released no-flag calls consult the Mailer's operational async setting; the builder default is false, and `.async()` changes it. An injected Mailer has no statically known mode. Require bounded construction evidence or an explicit scope policy. |
| Removing builder `.async()` | Conditional | Remove it only after accounting for all operations using that builder/Mailer. Do not erase the old policy while leaving dependent operations unresolved. The removed CLI `--mailer:async` setting needs a separate text finding. |
| Async receipt future to `MailSend.getCompletion()` | Conditional; follow-up | A completion future is only one facet of `MailSend`. Current `getCompletion()` is detached; cancellation of that future is not a request to cancel the send. |
| Old `CompletableFuture<Void>` wrappers | Report initially | A completion-only adapter such as `.getCompletion().thenApply(receipt -> (Void) null)` can retain a Java signature, but does not prove cancellation, completion mutation, ownership, or lifecycle equivalence. |
| `shutdownConnectionPool()` to `closeAsync()` | Report initially | A method rename is mechanically possible but changes lifecycle behavior. Final-shutdown intent must be established. |

The old [Mailer API](https://github.com/bbottema/simple-java-mail/blob/9.3.6/modules/core-module/src/main/java/org/simplejavamail/api/mailer/Mailer.java)
returns `CompletableFuture<Void>` from send methods and receipt futures from its receipt methods.
The current [Mailer API](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/Mailer.java) exposes
synchronous direct receipts and asynchronous [MailSend](../../modules/core-module/src/main/java/org/simplejavamail/api/mailer/MailSend.java)
handles. `requestCancellation()` is explicit. Public wrappers deserve review even if a return-type adapter compiles.

Inserting `.sync()` or `.async()` also changes where a null receiver fails relative to argument side effects.
The first release should reject unproven receivers or expressions instead of duplicating evaluation or assuming this
is irrelevant. Literal mode selection does not, by itself, establish exception or cancellation compatibility.

The released [shutdown implementation](https://github.com/bbottema/simple-java-mail/blob/9.3.6/modules/simple-java-mail/src/main/java/org/simplejavamail/mailer/internal/MailerImpl.java#L506)
shuts down an owned executor and cleans up pools, or returns a completed future where no pool cleanup is needed.
It does not establish the target's universal operation-admission and drain contract. The target
[Mailer implementation](../../modules/simple-java-mail/src/main/java/org/simplejavamail/mailer/internal/MailerImpl.java)
shuts down admission, drains operations, and then completes cleanup. Later use, externally supplied executors, and
shutdown inside callbacks all require examination; blindly introducing blocking close in a callback can deadlock.

Preparation timing differs within the source range too. In 9.0.0 async preparation could throw on the caller;
9.3.6 still prepares on the caller but catches runtime failures into a failed future; the 10.x async path prepares
during execution. Tests must identify their source version instead of asserting one universal 9.x behavior.

### Narrow typed candidates and report boundaries for grouping

These are proposed patterns and validation requirements, not implemented recipes. Broad grouping is excluded from
the first eight-rule composite; its future admission belongs to B6 in the plan.

- A fresh non-escaping library-created Mailer builder followed by a contiguous run of only pool setters with
  effect-free local/literal arguments can collect that run into one `ConnectionPoolConfig`. Prove that it has no
  earlier explicit pool choice, interleaved call, alias, read, build, branch or resource callback. Compose the
  independently required millis-to-`Duration` and factory migrations; do not claim one name change covers them.
- For a known existing builder local, changing max size alone must preserve supplied claim timeout, cluster key and
  expiry through its current group's `toBuilder()`. This is a conditional bounded-flow rewrite; a nullable/escaping
  builder, arbitrary receiver expression, intervening getter or an unknown earlier assignment blocks automation.
- T003's existing narrow literal rule can use the same technique for a final non-null local Email builder:
  `email.withDeliveryStatusNotificationNotifyOptions("FAILURE,DELAY")` becomes
  `email.withSmtpDeliveryOptions(email.getSmtpDeliveryOptions().toBuilder().withDeliveryStatusNotificationNotifyOptions(NotifyOption.FAILURE, NotifyOption.DELAY).build())`.
  Require exact old attribution and proven library ownership, preserve the return choice and prior notify edits, and
  reject fluent receiver expressions rather than evaluate them twice. This is part of T003, not a general group rule.
- T004 must map the three released static debug starters through a fresh `SessionDebugConfig` as part of the complete
  starter expression. Preserve output/printer identity, null behavior and independent activation; unsupported values
  or initialization/evaluation timing remain report-only. Renaming the declaring factory alone would leave removed setters.
- A positional crypto call with a stable non-null receiver and only already-evaluated local/literal arguments can be
  expressed with the existing typed value builders. Future fixtures must establish unchanged key-byte copying,
  nullable algorithms and eager file parsing/closing. Do not lift configuration construction out of a loop or change
  when key material is read. For null DKIM header exclusions, omit the setter on a fresh config builder or preserve the
  explicit Set type; a bare null is ambiguous against the builder's Set/varargs overloads. Do not substitute default signing/encryption policy.

finding until all effects are understood. Replacing an earlier released `withConnectionPoolClaimTimeoutMillis(...)`
choice and later size customization with separate fresh groups can lose the earlier timeout; inspect the whole

custom executors/factories, proxy ownership and active optional modules. Stable Java syntax cannot prove deployment
configuration or SMTP behavior. Property/Spring/CLI scalar keys and units retain their contracts; Java grouping does not authorize rewriting their

### Current target supplement: common failures and explicit acceptance predicates

The inspected released 9.3.6 `MailSubmissionReceipt.isAcceptedByServer()` tests `smtpResponse != null &&
smtpResponse.isPositiveCompletionReply()`. The removed intermediate 10.x method already meant status-based any-recipient acceptance.
Do not use that unreleased implementation as source evidence for an automatic 9.x rename. The final target has
`isAcceptedForAtLeastOneRecipient()` and `isFullyAcceptedForSubmission()`; only the first is true for PARTIALLY_ACCEPTED, and both are false
for UNKNOWN without establishing rejection. SMTP acceptance remains separate from final delivery and cleanup success.

R037 must ask what a released call intended. Choosing any/full status is semantic/report-only unless independently established. An exact
old positive-response test can be expressed as `receipt.getSmtpResponse().map(SmtpServerResponse::isPositiveCompletionReply).orElse(false)`
on the frozen target. This is only a conditional candidate after checking source-version semantics, attribution, receiver/evaluation/null behavior,
custom implementations and method references; no production recipe or new T responsibility is introduced. A safe typed any-to-any rename is
not claimed for the inspected released source. Merely matching the method name/type is insufficient.

The same topic covers changed exception handling. Released `EmailTooBigException` and `BatchTransportException` join `MailException`, and size
failures are no longer hidden by an outer sending wrapper. Admission rejection uses `MailSendRejectedException`, retaining an external executor's
original rejection. Catch reachability, related multi-catch alternatives, wrapper/cause assumptions, construction and future handling require
conditional/report-only review. Broadening a catch can also capture application-originated failures; provider causes and observer/completion
identity must survive. `getKind()` and the optional receipt accessor are new normal capabilities, not separate released migration obligations.
Kinds never prove retry safety, and a missing receipt never proves non-acceptance.

The released 9.3.6 single-send and simple-batch closures wrapped CustomMailer/iterator RuntimeExceptions in `MailerException` too.
The final target propagates those original application exceptions. R037 therefore includes broad catches whose former coverage included
application failures; do not mechanically widen them or change their recovery policy. Open-connection callbacks retain their documented boundaries.

Preserved additive/copying behavior, business correlation patterns, clear/reset documentation and completion-only streaming batches add no migration
topic. New transport presets and new-feature serialization also require no released migration entry without evidence of affected released behavior.
Retain R001-R047 and all eight proposed T responsibilities. The implementation plan adds F20 validation coverage for this existing R037 topic.

## Report companion: what OpenRewrite provides

OpenRewrite already supports custom [data tables](https://docs.openrewrite.org/authoring-recipes/data-tables).
A review recipe can insert a finding row while returning the original syntax tree unchanged. No custom Maven plugin
is required for this. The normal console primarily reports recipe activity, changed files, and patch locations;
it does not replace a linked, prioritized migration report.

Built-in searches, such as [FindMethods](https://docs.openrewrite.org/recipes/java/search/findmethods), commonly add
`SearchResult` markers rendered as `/*~~>*/`. In the tested Maven plugin 6.46.1, `runNoFork` wrote those markers into
the actual Java file. A marker-based review recipe is therefore unsuitable as the default source-preserving report.
Do not generalize documentation for a newer version into a guarantee for the pinned runtime.

The proposed companion should consume the data tables and produce a readable Markdown summary plus a stable JSON
representation. It should include source locations, reasons, confidence/evidence type, required actions, and guide
links. A later HTML renderer can consume the same representation. The companion does not perform transformations.

The report must also expose incomplete analysis: unresolved types, failed parsers, exclusions, unsupported languages,
unknown versions and missing modules. A zero-finding result with incomplete coverage is not a clean migration.
Runtime checklist items must survive a source rewrite; removal of an old method name is not proof that its behavioral
review is complete. Stable fingerprints should use rule, relative path and symbol context, rather than line alone.
Avoid storing credentials, arbitrary argument literals, complete source excerpts, or absolute user paths.

Maven's `exportDatatables` exports CSV files. The experiment produced them beneath
`target/rewrite/datatables/<timestamp>/`, and a dry-run patch at `target/rewrite/rewrite.patch`.
Documentation and plugin versions can differ on default locations, so the supported runner must capture the actual
run directory explicitly. `failOnDryRunResults` detects source differences; it does not gate unresolved rows emitted
by a table-only recipe. A report CLI must supply any finding-based exit policy.
See the [Maven plugin reference](https://docs.openrewrite.org/reference/rewrite-maven-plugin) and
[Gradle plugin configuration](https://docs.openrewrite.org/reference/gradle-plugin-configuration).
